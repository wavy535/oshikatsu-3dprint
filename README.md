# OshiNest（オシネスト）

推し活特化型 3Dプリント受託販売ECプラットフォーム

---

## 1. サービス概要

**OshiNest は「3Dモデルを作れる人」と「推しぬい・推し空間を飾りたい人」をつなぎ、印刷・検品・発送を運営が丸ごと代行するマーケットプレイスです。**

一般的な3Dモデル販売サイトは「STLデータを売る」ため、買った人が自分で3Dプリンタを用意して出力する必要があります。OshiNest はここを逆にし、**クリエイターは3Dデータ（3MF / STL）と印刷仕様を登録するだけ**、**購入者には完成した現物が届く**という形にしています。

- クリエイター：造形に集中できる。プリンタ・材料・梱包・発送の負担ゼロ
- 購入者：3Dプリンタを持っていなくても、推しぬいのサイズに合った台座や小物が手に入る
- 運営：印刷・品質管理・配送を一元管理し、印刷代行費とプラットフォーム手数料で収益を得る

### 想定ユーザー

| | ペルソナ | 課題 |
|---|---|---|
| 購入者 | 推しぬい（10/15/20cm）を持ち、写真映えする台座・背景・小物を探している人 | 既製品はサイズが合わない。ハンドメイド品は数が少なく高い |
| クリエイター | Blender等でモデリングできるが、出力環境や発送の手間がネックで販売に踏み切れない人 | プリンタ・材料費・梱包・発送・トラブル対応がすべて自分持ち |

## 2. 登場人物と権限

| ロール | できること |
|---|---|
| `buyer`（購入者） | 作品閲覧・検索・お気に入り・フォロー・購入・レビュー・オーダーメイド相談 |
| `creator`（クリエイター） | buyer の全機能 + 作品投稿・作品管理・売上ダッシュボード・振込申請・相談対応 |
| `admin`（運営） | 注文管理・STLダウンロード・印刷ステータス更新・追跡番号登録・クリエイター申請の審査 |

- 1アカウントで購入者とクリエイターを兼務します（別アカウント不要）
- `buyer → creator` は**申請 → 運営審査 → 承認**で昇格します（`creator_applications` テーブル + 承認トリガーで `profiles.role` を更新）

## 3. お金の流れ

```
購入者の支払額 = 販売価格 + 印刷代行費 + 送料（税込）

印刷代行費   = 材料量(g) × ¥3.5 + 造形時間(h) × ¥75 + パーツ数 × ¥20
運営手数料   = （購入者の支払額 − 印刷の実費 − 送料の実費）× 手数料率(20%)
クリエイター受取額 = 購入者の支払額 − 印刷の実費 − 送料の実費 − 運営手数料
```

手数料は「販売価格の◯%」ではなく、**支払額から印刷と送料の実費を引いた残りにかけます**（`0015` / `0016`）。式は `order_settlements` ビューだけが持ち、発送後に実費で確定します。それまでは見積り額での見込みです。

**印刷代行費は一律ではなく、アップロードされた3Dデータから自動算出します。** 体積は寸法の3乗で増えるため、一律料金にすると大きい作品で必ず赤字になります。

**そのうえで、代行費は購入者に別建てで請求します。** サイズによって代行費が数倍変わるサービスでは、代行費を販売価格に含めるとクリエイターが「デザインの値段」を決められません（15cm のジオラマだと販売価格 ¥5,200 のうち ¥4,616 が代行費で、手取りは ¥64 にしかならない）。分けておけば、クリエイターはサイズに関係なく自分の値付けだけを考えればよくなります。

課金モデルは `print_pricing_rules.fee_billing` で切り替えられます（`separate` が既定 ／ `bundled` は販売価格に含める旧方式）。`bundled` のときだけ「代行費と手数料を回収できない価格は保存できない」下限チェックが働きます。

| | 小さい台座 | ジオラマ（6パーツ・15cm） |
|---|---|---|
| 材料量 / 造形時間 | 27 g / 3.3 h | 438 g / 39.5 h |
| 印刷代行費 | ¥360 | **¥4,616** |
| 販売価格の例 | ¥1,800 | ¥5,200 |
| 購入者の支払額（送料別） | ¥2,160 | ¥9,816 |
| クリエイター受取額（実費が見積り通りのとき） | ¥1,440 | ¥4,160 |

投稿画面には受取額シミュレーションを常時表示し、価格を入力した時点で手取りが分かるようにしています。精算は発送後に実費で確定し、クリエイターが振込申請 → 運営が処理して指定口座へ送金します。

代行費の実額は運営側でも記録します。印刷ジョブに実使用フィラメント量・実造形時間・失敗回数を入力させ、見積り（`est_*`）と実績（`actual_*`）の差から単価係数を見直せるようにしています。

## 4. 主な機能

### 購入者向け
- アカウント登録／ログイン（メール＋パスワード、SNS連携）
- **マイぬい**の登録（名前・種類・座高・肩幅・抱き幅を手入力）→ メインのぬいのサイズで一覧を絞り込み、作品ごとにサイズの相性を数値で判定
- （構想・保留）**うちの子で見る**：アストラ連携でぬいを撮って3Dモデルを生成し、作品を開くとその作品にうちの子が置かれた状態で見える
- 作品検索・絞り込み（カテゴリ／対応ぬいサイズ／世界観タグ／価格帯／評価／在庫）
- お気に入り、クリエイターのフォロー
  - お気に入り一覧は**お気に入りが多い順／追加した順／価格順／評価順**で並べ替え。値下げ・出品停止・在庫切れがカード上で分かる
  - 作品カードにはいいね数を表示し、一覧・検索でも「お気に入りが多い順」で並べ替えできる
- カート・決済（クレジットカード／コンビニ／キャリア決済）
- 注文ステータス追跡、**受け取り評価**（受け取り確認＋レビュー投稿）
  - 項目別評価は**クリエイターへの評価**（デザイン・完成度／説明との一致／サイズ感）。印刷・梱包・配送は運営の担当なので、別枠の任意入力として分けています
- クリエイターへのメッセージ、オーダーメイド相談
- 推し空間コーディネート投稿（自分の飾り方を投稿し、使用パーツをピン留め）

### クリエイター向け
- クリエイター申請（SMS で電話番号を認証 → クリエイター利用規約に同意 → 運営が審査）
- 作品投稿（4ステップ：①データ検証 → ②印刷指示 → ③作品情報・サイズ展開 → ④公開）
  - 3Dデータ（3MF / STL）は**非公開バケット**に保存。購入者にもダウンロードさせない
  - アップロード時に**自動検証**（マニフォールド／法線／単位／肉厚／ベッドサイズ／色数）
  - **色スロット**を在庫のあるフィラメントに割り当て（自由記述ではなく選択制）
  - **パーツごとの積層方向・サポート・回転禁止**と組立図を登録
  - **サイズ展開**（10/15/20cm）を1投稿で出し分け。価格・在庫・代行費はサイズごと
  - **オーダーメイド対応設定**（カラー変更／配置反転／設置用スタンドホール／中間サイズ相談）
- 作品管理（公開中・下書き・非公開の切替、販売数・閲覧数の確認）
- 売上ダッシュボード（月次売上、販売点数、受取予定額、フォロワー推移）
- 振込先口座の登録と振込申請

### 運営向け（Admin）

運営コンソールは購入者向け UI と視覚的に分離しています（ダークヘッダー＋「運営コンソール」バッジ）。

- **印刷キュー**：未着手／印刷中／検品待ち／期限超過の KPI、素材・色・プリンタでの絞り込み、期限順のジョブ一覧
- **印刷ジョブ詳細**：パーツごとの推奨積層方向・サポート要否・分割組立図、色スロットの在庫引き当て、スライス設定、実績（実使用 g・実時間・失敗回数）の記録
- **検品・発送登録**：6項目のチェックリスト、検品写真、NG時の原因分類と再印刷指示、梱包情報、配送業者・追跡番号の登録
- フィラメント在庫・プリンタ台帳の管理
- クリエイター申請の承認・却下

再印刷の原因は `model`（クリアランス不足など作品データ側）／`print`／`material`／`handling` から選ばせます。`model` を選ぶとクリエイターに修正依頼が飛び、再印刷分の代行費は運営負担になりません。この分岐がないと、モデル側の不備による刷り直しコストがすべて運営に乗ります。

全画面のヘッダーロゴには Top へ戻るプロトタイプリンクを、ヘッダーのベルには通知一覧へのリンクを張ってあります。サイドバーの全行も対応する画面へつないであり、押しても何も起きない行はありません。並びは使う頻度順で、購入履歴 → 通知 → お気に入り → メッセージ → マイぬい → 配送先・お支払い → 通知設定 → （クリエイター）作品管理 → 売上管理 → プロフィール編集 です。

## 6. 主要フロー

### 購入フロー

```
作品詳細 →［カートに追加］→ カート →［レジに進む］→ 決済
  →［注文を確定する］→ マイページ（購入履歴）
      決済完了 → 印刷中 → 発送済み →［発送済みをタップ］→ 受け取り評価 → 取引完了
```

レビューは**商品が届いてから**書くものなので、決済直後ではなくマイページの注文行から入る導線にしています。注文ステータスが `発送済み` になると、その行のステータス表示自体がボタンになり、受け取り評価画面へ遷移します。

### 出品フロー

```
クリエイター申請 → 運営が審査 → 承認（role: buyer → creator）
  → STEP1 3Dデータのアップロード・自動検証（代行費が自動算出される）
  → STEP2 色スロットの割り当て・パーツごとの印刷指示・組立図
  → STEP3 作品情報とサイズ展開（サイズごとに価格・在庫を設定）
  → STEP4 サムネイル選択・公開
  → 注文が入る → 運営が印刷指示どおりに造形・検品・発送 → 売上に計上 → 振込申請
```

### オーダーメイドフロー

```
作品詳細／クリエイタープロフィール →［オーダーメイド相談］→ 相談フォーム送信
  → メッセージで仕様を詰める → クリエイターが見積りを提示（custom_order_quotes）
  →［承認して支払いに進む］→ accept_custom_quote() が購入者専用の work_variant を作成
  → 通常のカート・決済フローに合流 → 以降は同じ
```

見積りには有効期限があり、1つの相談に「提示中」の見積りは1件までです（部分ユニークインデックスで担保）。承認で作られるバリアントは `stock=1 / is_listed=false` なので、他の人が買うことはできません。代行費は見積り作成者が手で入れるのではなく、材料量と造形時間からトリガーが計算します。

### 修正依頼フロー（検品NGが作品データ由来だったとき）

```
運営が検品NG → 原因に「モデル側」を選ぶ
  → create_revision_from_qc() が revision_requests を自動生成
  → 該当サイズを自動で出品停止（同じ不良を刷り続けないため）
  → クリエイターの修正依頼画面に届く
      ① データを修正して差し替える（STEP1に戻って再検証）
      ② 印刷指示だけ変更する
      ③ このサイズを一時的に出品停止のままにする
```

原因が `print` / `material` / `handling`（＝運営側）のときは修正依頼を作らず、代行費もクリエイターに請求しません。`charged_to_creator` は原因から自動で決まるので、運用で取り違えることがありません。

### 通知フロー

通知は独立した機能ではなく、これまでの各フローが発火させる「副産物」として設計しています。画面を新しく足したのではなく、すでにある状態遷移に受け皿を用意した、という位置づけです。

| きっかけ（既存のトリガー） | 通知の種類 | 通知から開く画面 |
|---|---|---|
| `shipments` に行が入る（発送登録） | 注文・配送 | 注文詳細 |
| 印刷ジョブが `printing` に | 注文・配送 | 注文詳細 |
| `sync_work_min_price()` で最安値が下がる | お気に入り | 作品詳細 |
| メッセージの受信 | メッセージ | メッセージ |
| 注文明細の確定（売れた） | クリエイター | 売上ダッシュボード |
| `create_revision_from_qc()` で修正依頼が発生 | 修正依頼 | クリエイターの修正依頼 |
| レビューの投稿 | レビュー | 公開プロフィール |
| `custom_order_quotes` が `sent` に | オーダーメイド | オーダーメイド見積り |

発火はすべて DB のトリガーです（`shipments` / `print_jobs` / `works` / `messages` / `order_items` / `revision_requests` / `reviews` / `custom_order_quotes`）。アプリ側から `push_notification()` を呼ぶ形にしていないのは、呼び忘れで通知が届かない事故を防ぐためです。同じ出来事で二重に通知しないよう `(user_id, source_table, source_id, kind)` に部分ユニークインデックスを張っています。

設計上の判断が2つあります。

1. **取引に関わる通知はアプリ内でオフにできない。** 発送・修正依頼・入金は、届かなかったこと自体がトラブルになります。通知設定では「常時オン」のバッジを付け、トグルを淡色の固定表示にしてあります。オフにできるのはメールとプッシュだけです。
2. **通知は行き先を必ず1つ持つ。** 「◯◯しました」で終わる通知は、読んだ人が次に何をすればいいか分からず、結局サポートへの問い合わせになります。通知一覧の各行は上の表の遷移先を持ち、プロトタイプでもそこまでつないであります。DB では `notifications.link_path` を NOT NULL にして、行き先のない通知をそもそも作れなくしました。

まとめ受信（毎日20:00に1通）を用意したのは、値下げ・再入荷のようにそれ自体は急がない通知が、発送通知と同じ頻度で届くとメールが読まれなくなるためです。

## 7. 注文ステータス定義

注文のステータスは運営が手で更新するのではなく、印刷ジョブと発送記録から自動で導出します。二重管理で食い違うのを避けるためです。

| ステータス | 意味 | 遷移のきっかけ |
|---|---|---|
| `payment_pending` 決済待ち | 注文作成直後 | 購入者が注文を確定 |
| `paid` 決済完了 | 支払いが確定 | 決済プロバイダの webhook |
| `printing_queued` 印刷待ち | 印刷ジョブを生成 | `create_print_jobs_for_order()` |
| `printing` 印刷中 | いずれかのジョブが印刷中 | ジョブが `printing` / `reprinting` に |
| `packaging` 発送準備中 | 全ジョブが検品OK | 全ジョブが `qc_passed` に |
| `shipped` 発送済み | 追跡番号を登録し発送 | `shipments` に行が入る |
| `completed` 取引完了 | 購入者が受け取り評価を確定 | 購入者 |
| `cancelled` / `refunded` | キャンセル・返金 | 運営 |

印刷ジョブ側のステータスは `queued → printing → printed → qc_passed`、検品NGなら `qc_failed → reprinting → printed → …` とループします。遷移はすべて `print_job_events` に記録されます。

## 9. 3Dデータ・印刷仕様・サイズ展開

投稿フローの STEP1・STEP2・STEP3 を支える部分です。実データ（6オブジェクト・2色・438g のジオラマ）で検証済みの仕様を反映しています。

### 対応フォーマット

| 形式 | 用途 | 制約 |
|---|---|---|
| `.3mf`（推奨） | 多色・複数パーツ | 色定義と複数オブジェクトを1ファイルで持てる |
| `.stl` | 単色・1パーツ | 三角形座標しか持てないため色を表現できない |

`.stl` だけを受け付ける設計では、2色構成や6パーツ構成の作品を投稿できません。

### 自動検証（STEP1）

アップロード時に `work_asset_objects` と `work_validation_issues` を生成します。

| コード | 内容 |
|---|---|
| `manifold` | 閉じたソリッドか（開エッジ数） |
| `normals` | 反転した法線の面数 |
| `unit` | 単位・スケール（3MFの `unit` 属性。mm実寸か） |
| `thickness` | 最小肉厚 |
| `bed_size` | ベッド（既定 220×220×250 mm）に載るか |
| `batch` | 造形時間からのバッチ数 |
| `colors` | 検出した色数 → 必要なフィラメントスロット数 |

### 検証パイプラインの実装

`src/lib/print/` に、依存ライブラリなしの解析エンジンを置いています。3MF は ZIP コンテナなので、ZIP の中央ディレクトリ読み取りと `zlib.inflateRawSync` で `3D/3dmodel.model` を取り出し、汎用 XML パーサを使わずに必要なタグだけを走査します（31万三角形のファイルで解析全体が約3秒）。

| ファイル | 役割 |
|---|---|
| `zip.ts` | 3MF コンテナの読み取り（deflate / 無圧縮のみ、ZIP64・暗号化は明示的にエラー） |
| `threemf.ts` | `3dmodel.model` の走査。オブジェクト・色定義（`basematerials` / `colorgroup`）・`build` の transform 展開 |
| `stl.ts` | バイナリ / ASCII STL。三角形数とファイルサイズの一致で形式を判定 |
| `mesh.ts` | 解析で扱う共通のメッシュ表現と行列演算 |
| `analyze.ts` | 頂点溶接、エッジ対応によるマニフォールド判定、符号付き体積・表面積、肉厚、面の重なり |
| `estimate.ts` | フィラメント量・造形時間・代行費・ベッド判定・サイズ展開 |
| `index.ts` | 上記をまとめ、`work_validation_issues` に入る形の検証結果を返す |
| `src/lib/works/asset-validation.ts` | Storage からのダウンロード → 解析 → DB書き込み |
| `src/lib/works/actions.ts` | STEP1 の「検証する / 再検証」から呼ぶ Server Action（所有者チェック付き） |

**検証項目**（すべて `severity` 付きで1行ずつ返す。OK の項目も返すので、STEP1 のチェックリストがそのまま描ける）

| code | 内容 | 判定方法 |
|---|---|---|
| `manifold` | 穴・非多様体エッジ | 頂点を溶接し、無向エッジの共有枚数が 1（穴）か 3以上（非多様体）かを数える |
| `normals` | 巻き順の不一致・全体の裏返り | 同じ向きの有向エッジが2回出る面を数える。符号付き体積が負なら全体が内向き |
| `unit_scale` | 単位とスケール | 3MF は `unit` 属性。STL は単位を持たないので mm と解釈し警告。最大寸法 5mm 未満はエラー |
| `min_thickness` | 薄すぎる壁 | 面の重心から内向きにレイを飛ばし、正面から向かい合う面までの距離を測る |
| `self_intersection` | 面の重なり | 三角形の辺が他の三角形を貫いているかを、空間グリッドで候補を絞って調べる |
| `build_size` | ベッドに載るか | **パーツ単体**の寸法で判定（分割パーツは別々に刷るため） |
| `color_info` | 色数 | 3MF の色定義を色スロットに展開。STL は単色 |
| `batch_count` | 造形回数 | 推定造形時間を1バッチ上限時間で割る |

肉厚の判定には実データで2つ落とし穴がありました。ひとつは、隣り合う面や凹んだ角をレイが拾って厚み 0mm と出てしまうこと（頂点を共有する面を除外し、向かい合う角度が60度以内のヒットだけを採用して解決）。もうひとつは、ブーリアン和を取らずに重ねたパーツの「内部の面」から測ってしまうこと（外側に出た点が材料の中かをレイの交差回数で判定して除外）。

さらに、三角形1枚のスライバーで弾くと誤検知だらけになるため、**面積で重み付けした下位1パーセンタイル**を実用上の最小肉厚として使い、しきい値未満の面が表面積の2%以上を占めるときだけエラーにしています。

### 見積りと印刷代行費

材料量は外殻＋充填から推定します（`estimate_filament_grams`）。

```
材料体積 = min(表面積 × 殻厚0.09cm, 体積) + 残りの体積 × 充填率0.15
推定重量 = 材料体積 × 密度1.24 g/cm³
```

実データでスライサー実測 438g に対し推定 460g（**誤差 +5.2%**、オブジェクト単位で計算した場合）でした。

代行費は `calc_print_fee` で自動算出します。一律料金ではありません。

```
印刷代行費 = 材料量(g) × ¥3.5 + 造形時間(h) × ¥75 + パーツ数 × ¥20
```

単価は `print_pricing_rules` の `is_active` な行が使われます。単価を変えても過去の注文金額が動かないよう、`order_items` に金額をスナップショット保存します。

### サイズ展開

`work_variants` が「実際に売る単位」です。体積は寸法の3乗で増えるため、代行費もサイズごとに再計算されます。実データでの算出結果：

| サイズ | 倍率 | 最大寸法 | 材料 | 造形時間 | 代行費 | 価格下限 | 判定 |
|---|---|---|---|---|---|---|---|
| 10cm | 67% | 140 × 140 × 70 mm | 170 g | 15.3 h | ¥1,863 | ¥2,070 | 出品可 |
| 15cm | 原寸 | 210 × 200 × 105 mm | 438 g | 39.5 h | ¥4,616 | ¥5,129 | 出品可 |
| 20cm | 133% | 280 × 280 × 140 mm | 865 g | 78.0 h | ¥8,998 | ¥9,998 | **ベッド超過で出品不可** |

`work_variants` への書き込み時にトリガー `sync_work_variant` が走り、次を自動で行います。

- 代行費の再計算
- ベッドに載るかの判定（載らなければ `is_printable = false`、`is_listed` を強制的に false）
- 造形時間からのバッチ数算出（ベッド面積の都合がある場合は `batch_count_override` で上書き）
- **価格の下限チェック** — 代行費と手数料を回収できない価格は例外で弾く

```
下限価格 = ceil(印刷代行費 ÷ (1 − 手数料率))
クリエイター受取額 = 販売価格 − 印刷代行費 − 販売価格 × 手数料率
```

画面用には `work_variant_pricing` ビューが下限価格と受取額を付けて返します。

### マイぬいとサイズの絞り込み

`work_variants.nui_size_cm` は「何cmのぬい向けか」を持っていますが、購入者側は自分のぬいが何cmなのかを毎回思い出さないと絞り込めません。そこでマイぬい画面で採寸値を登録しておき、一覧の既定フィルタにする形にしました。

| 登録する値 | 何に効くか |
|---|---|
| 座高 | いす・ベッド・テーブルの高さ。`nui_size_cm` の判定に使う主値 |
| 肩幅 | 衣装ラック・ソファの幅 |
| 抱き幅 | ドア・通路・箱の幅。梱包サイズの判定にも使う |

メインに設定したぬいのサイズが、Top と検索結果の「対応ぬいサイズ」の初期値になります（`popular_works(p_nui_size_cm)` の引数）。複数体を登録できるのは、推しが増えたときにサイズ違いを並行して買うためです。ヘッダーの「マイぬい」からも同じ画面に入ります。

### うちの子で見る（アストラ連携）— 構想（保留中）

> **いまは保留です。** アストラ側の連携方式が確定していないため、本線から外して Figma の ⑦ レーンに参考として残してあります。マイぬいは当面「手入力で採寸値を登録するだけ」で、作品詳細に合成イメージへの導線は置いていません。
> DB は `0010` で作ってあるので（`nui_scans` / `nui_assets` / `tryon_renders`）、連携方式が決まれば撮影と生成の部分だけ足せば動きます。**相性判定（`fit_*_mm` と `nui_fit_*()`）はアストラに依存しないので、いまも使えます。**

以下は保留時点での設計メモです。

「買ってみたら大きすぎた／小さすぎた」が、このサービスで一番起きやすい失敗です。サイズ表記だけでは、推しのぬいが実際にその椅子に座れるのかが分かりません。そこで **アストラ（カメラ越しのAIアシスタント）と連携してぬいを撮影 → 3Dモデルを生成 → 作品を開くと、その作品にうちの子が置かれた状態で見える** ようにします。

合成の向きは「ぬい → 作品の中へ」です。作品を自分の部屋に置くAR（逆向き）ではありません。飾る場所ではなく、**うちの子が収まるかどうか**が買う前に知りたいことだからです。

#### フロー

```
マイぬい［＋ アストラでスキャン］
  → ① アストラと連携（スマホ側のカメラを使う許可）
  → ② 4方向から撮影（正面・右横・背面・斜め＋座り姿勢）
        アストラが構図を案内し、手ぶれ・逆光・見切れは自動で撮り直しを促す
  → ③ 3Dモデルを生成（数十秒）
  → ④ 採寸値の確認（座高・肩幅・抱き幅を自動で読み取り、手で直せる）
  → マイぬいに「スキャン済み」として登録

作品詳細［うちの子で見る］
  → 合成ビュー（正面／斜め／横／実寸で比べる）
  → ぬいの切り替え・サイズの切り替えで再合成
  → サイズの相性を3項目で判定
  → ［この見え方でカートに入れる］
```

#### サイズの相性判定

判定は生成画像の見た目ではなく、**数値の比較**で出します。画像はあくまで納得のための表現で、可否の根拠にはしません。

| 比較 | 使う値 | 判定の例 |
|---|---|---|
| 幅 | 作品の内寸（座面の幅など） vs ぬいの抱き幅 | 12.4 / 12.0cm → ぴったり |
| 高さ | 作品の内寸（背もたれの高さなど） vs ぬいの座高 | 16.2 / 15.0cm → 余裕 1.2cm |
| 奥行 | 作品の内寸（座面の奥行） vs ぬいの抱き幅 | 10.5 / 12.0cm → 足が前に出ます |

これを出すには **作品側に「ぬいが収まる内寸」が必要** です。外形の `bbox_*_mm` では「入るかどうか」は分かりません。`0010` で `work_variants.fit_width_mm / fit_height_mm / fit_depth_mm` を足し、STEP3 の右カラムに入力欄を置きました。原寸だけ入れれば、他のサイズは `scale_ratio` を掛けてトリガーが自動で埋めます（`fit_source='auto'`）。

判定のしきい値は `judge_axis()` に置いてあり、画面の文言と1対1で対応します。

| 余裕 | 判定 | 画面の表示 |
|---|---|---|
| マイナス | `too_small` | 「◯◯には小さすぎます」 |
| 5mm 未満 | `tight` | 「ぴったり収まります」 |
| 5〜40mm | `good` | 「この子にちょうどいい」 |
| 40mm 超が2軸以上 | `loose` | 「余裕はあるが大きめ」 |
| 内寸が未入力 | `unknown` | 「内寸が未登録のため判定できません」 |

総合判定は幅と高さを必須条件にし、奥行だけ足りない場合は「足が前に出ます」として通します。座らせられるなら買う人がいるからです。内寸が未入力のバリアントは `variants_missing_fit_dims` ビューで拾えます。

#### 想定するデータ

`0010_notifications_and_nui.sql` で作成済みです。

| テーブル | 役割 |
|---|---|
| `nui_profiles` | ぬい1体。座高からサイズ区分を自動で決め、1体目は自動でメインになる |
| `nui_scans` | 1回のスキャン。撮影枚数・生成状態・自動採寸値・確からしさ・写真の失効日 |
| `nui_assets` | 撮影写真と生成物。非公開バケット `nui-scans`（本人以外は読めない） |
| `tryon_renders` | （ぬい × バリアント × 視点）の合成結果のキャッシュ。作品データが差し替わると自動で消える |
| `work_variants` への追加 | `fit_width_mm` / `fit_height_mm` / `fit_depth_mm` / `fit_source` |

#### 写真とデータの扱い

- 撮影した写真は生成が終わったら 30日で自動削除する
- 生成した3Dモデルは合成イメージの生成にだけ使い、公開プロフィールにも作品ページにも出さない
- 合成イメージは本人だけが見られる。クリエイター側にも渡さない

画面にもこの3点を明記しています。人の部屋や本人が写り込みやすい撮影なので、ここを書かずに撮影を求めるのは避けたいところです。

写真の失効は `nui_scans.photos_expire_at`（既定で30日後）に持たせ、RLS は全テーブル本人限定です。

#### 未確定

- アストラ側の連携方式（アプリ間連携か、Webからのカメラ起動か）
- 生成の実行場所（端末側か、サーバー側のジョブか）と課金
- 合成の品質が出ない作品（透明パーツ・複雑な内部構造）をどう扱うか
- 既存の出品作品の内寸をどう埋めるか（クリエイターへの一括依頼か、メッシュからの推定か）

### サイズ専用データ

薄肉やほぞのクリアランス（例：片側0.3mm）は等倍スケールに耐えません。`work_variants.asset_id` に別の `work_assets` を指定すると、そのサイズだけ専用データで印刷できます。NULL なら基準データを `scale_ratio` でスケールします。

### 色スロット

`work_color_slots` が 3MF の色定義（例：White `#F7F5F0` / Black `#424045`）を `filaments` の在庫に紐づけます。自由記述ではなく**在庫のある色からの選択制**なので、調達できない色の注文が入りません。

## 10. 技術構成

- **アプリケーション**：Next.js 16（App Router）+ TypeScript + Tailwind CSS v4。読み取りは RSC、変更系は Server Actions、外部からの受信（cron・Webhook）は Route Handlers
- **UI**：Shadcn UI 互換のコンポーネント基盤（`src/components/ui`）
- **バックエンド**：Supabase（Auth / PostgreSQL / Storage / RLS / pg_cron）。集計・状態遷移・通知はすべて DB のトリガーと関数が持つ
- **ホスティング**：AWS Amplify Hosting（Next.js の SSR に対応）。定期実行は Amazon EventBridge のスケジュールルールから API Destination 経由で `/api/cron/*` を呼ぶ
- **メール**：Resend（開発時は Mailpit）
- **決済**：現在は開発用の即時確定（`confirm_order_payment()` を直接呼ぶ）。Stripe Checkout + Webhook は本番前にキーを入れて有効化する（下記「今後」）
- **セッション管理**：`src/proxy.ts`（Next.js 16 の旧 `middleware.ts`）でセッション更新と保護ルートのガード

保護ルート（`src/lib/supabase/proxy.ts`）：`/mypage`, `/creator`, `/admin`, `/checkout`。`/studio` はレイアウト側で役割を検査

## 12. セットアップ

### ローカルで動かす（Supabase はローカルコンテナ）

Docker Desktop が必要です。

```bash
npm install
cp .env.local.example .env.local   # ローカルの Supabase の値を設定（下記）
npx -y supabase@2.116.0 start      # 初回・停止後。API 54421 / DB 54422 / Studio 54423 / Mailpit 54424
npx -y supabase@2.116.0 db reset   # supabase/migrations を順に適用し、supabase/seeds を投入
node scripts/seed-storage.mjs      # ダミー画像を Storage へ（db reset では戻らない）
npm run dev                        # http://localhost:3000
```

- ポートは既定の 5432x ではなく 544xx に寄せてあります（`supabase/config.toml`）。`config.toml` を変えたら `stop` → `start`
- シードのアカウントはパスワード共通 `password123`：`buyer@example.com` / `creator@example.com` / `creator2@example.com` / `admin@example.com`
- 新規登録は6桁の確認コード方式。コードは Mailpit（http://127.0.0.1:54424）で受け取れます
- クリエイター申請の SMS 認証は、ローカルでは `config.toml` の `[auth.sms.test_otp]` にある番号だけ通ります（`090-0000-0001`〜`0003`、コードは `123456`）
- `.env.local` の Supabase の値は `npx supabase status` で表示されるものを使います。Stripe の値は空のままでよく、空なら決済は開発用の即時確定になります

### 環境変数

| 変数 | 用途 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ブラウザ・サーバー共通の Supabase 接続 |
| `SUPABASE_SERVICE_ROLE_KEY` | サーバー専用。cron・メール送信などユーザー文脈が無い処理だけで使う |
| `NEXT_PUBLIC_SITE_URL` | メール内リンクや決済のリダイレクト先 |

| `RESEND_API_KEY` / `MAIL_FROM` | 通知メールの送信。`RESEND_API_KEY` が無ければ開発時は Mailpit へ |
| `STRIPE_SECRET_KEY` / `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` / `STRIPE_WEBHOOK_SECRET` | 今後。入れると決済が Stripe Checkout に切り替わる |

### 本番（Supabase クラウド）へのマイグレーション適用

```bash
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

`supabase/migrations/0001〜0026` を CLI が番号順に適用します。Authentication > URL Configuration のリダイレクト URL に本番ドメインの `/auth/callback` を追加してください。

クリエイター申請の SMS 認証には SMS プロバイダが要ります。Authentication > Providers > Phone で Twilio などを設定し、「Confirm phone」を有効にしてください（アプリ側に鍵は不要です）。

### 本番（AWS）へのデプロイ

1. **Amplify Hosting** で GitHub のこのリポジトリを接続する（フレームワークは Next.js SSR として自動検出）。環境変数に上表の値を入れる。`NEXT_PUBLIC_SITE_URL` は Amplify のドメイン
2. **EventBridge** にスケジュールルール（`rate(10 minutes)`）を作り、API Destination の宛先を `https://<ドメイン>/api/cron/dispatch-emails`、Connection の認証を `Authorization: Bearer <CRON_SECRET>` にする
3. Supabase の pg_cron（見積りの期限切れ・JST 00:05）は DB 側で動くので、AWS 側の設定は不要
4. Stripe を有効化するときは、Webhook の宛先を `https://<ドメイン>/api/stripe/webhook` にして `STRIPE_WEBHOOK_SECRET` を入れる

```bash
npx supabase gen types typescript --local > src/types/database.ts
```

`src/types/database.ts` は生成物です（手で直さない）。アプリからは `src/types/db.ts` 経由で参照します。
