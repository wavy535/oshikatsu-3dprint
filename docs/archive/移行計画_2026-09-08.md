## 0. 前提の整理

**この決定で捨てるもの**: `oshikatsu-3dprint` のアプリ実装 20,531行（カート・決済・注文・
発送・精算・検索・メッセージ・コーデ投稿・運営コンソール）と、マイグレーション23本 3,032行。
**ただし消さない**。ブランチ `feat/app-new-design` に8コミットで残してあるので、
画面ごとの実装は「読んで写す」ことができる。

**この決定で得るもの**: works 系スキーマ48テーブル。新デザイン前提で設計されていて、
案Aに無かった通知・採寸/相性判定・代行費のDB計算・お気に入りランキング・
検品の原因分岐が最初から入っている。

**いま何が動くか**: 認証・クリエイター申請だけ（6ルート）。
`npm run build` は通る（2026-09-08 実測）。

### 作業の実体は「DBはある、画面が無い」

案Bは**スキーマが完成していてアプリ層が空**という状態。したがって移行作業は
「ゼロから設計する」ではなく、**oshikatsu-3dprint の画面とロジックを、works 系の
名前に読み替えながら写す**という単純作業が主になる。設計の判断は済んでいる。

## 2. 進める順

各フェーズは「移植元を読む → works 系に読み替えて書く → build/lint → 画面で確認」。
プロトタイプ（`oshikatsu-3dprint/docs/screen-flow.html`）が見た目の正なので、
実装のたびに同じ画面を開いて突き合わせる。

### Phase 0: 動く土台（ここが済むまで画面は書かない）

1. `supabase/config.toml` を作る。**oshikatsu-3dprint と同時に立てるのでポートをずらす**
   （あちらは 54321-54329）。`project_id = "osinest"`、api 54331 / db 54332 /
   studio 54333 / inbucket 54334 あたり
2. `npx supabase db reset` で 0001〜0010 を流す
3. `npx supabase gen types typescript --local > src/types/database.ts`
   （いまの `database.ts` は手書きなので、生成物に置き換える）
4. `.env.local` を実際の値で埋める（いまは `.env.local.example` のプレースホルダのまま）
5. seed を書く。移植元の `supabase/seed.sql` を works 系へ読み替えるのが速い

**Docker が起動していないと何も進まない。** PATH は
`export PATH="$PATH:/c/Program Files/Docker/Docker/resources/bin"`。

### Phase 1: 共通シェルとデザイントークン

移植元: `feat/app-new-design` の1本目 `ebb0d8c`。
`globals.css` のトークン、`components/layout/{site-header,side-nav,site-footer}`、
`features/layout/queries.ts`、ルートグループ `(shop)/(account)/(creator)/(admin)`。

**ここはDB名の読み替えがほとんど無い**ので、ほぼそのまま持ってこられる。
未読数だけ `unread_notification_count()` を呼ぶ形に変える（移植元には通知が無い）。

依存の差: 移植元は base-ui + sonner + nuqs を使っている。osinest は Radix + shadcn。
**トースト（sonner）とクエリ状態（nuqs）は入れる**。ここで揃えておかないと後の画面が全部詰まる。

### Phase 2: 作品を見る

Top / 検索結果 / 作品詳細 / レビュー / Q&A・発送 / お気に入り一覧。

- 検索は `popular_works()` があるので「お気に入りが多い順」はDB側で済む
- 作品詳細の「マイぬいとの相性」は `nui_fit_for_work()` を呼ぶだけ。
  移植元には無い画面なので、プロトタイプの `#s-detail` を見て組む
- レビューとQ&Aは別画面に切り出す（Figma 34・35）。`qna_threads` がある

### Phase 3: 買う

カート / 決済 / 注文詳細 / 受け取り評価。

- Stripe は移植元の Checkout + Webhook をほぼそのまま使える。
  ただし注文確定後に `create_print_jobs_for_order()` を呼ぶ形に変える
- 注文ステータスは列を更新せず `sync_order_from_jobs()` の導出に任せる（設計判断9）
- レビューはクリエイター向けと運営向けを分ける（設計判断8。0008 で対応済み）

### Phase 4: 出品

STEP1〜4 / 作品管理 / 修正依頼 / 売上ダッシュボード。

- **STEP1 は osinest 側が強い**。`src/lib/print/` が 3MF/STL を実際に解析するので、
  移植元の STL only 実装は使わない。画面だけ移植元から持ってくる
- STEP2 の印刷指示は `work_part_instructions` へ。移植元は product_assets の列だった
- STEP3 の内寸は原寸だけ入力し、他サイズは `scale_ratio` でトリガーが埋める（設計判断6）
- 修正依頼は `revision_requests`。検品NGが `model` のときだけ飛ぶ（設計判断7）

### Phase 5: 運営オペレーション

印刷キュー / 印刷ジョブ詳細 / 検品・発送登録。

- 検品は `qc_check_definitions` の定義を読んでチェック項目を出す
  （移植元は6項目ベタ書き。osinest は定義テーブルから引く）
- 発送登録は `apply_shipment()`、検品結果は `apply_qc_result()`

### Phase 6: マイページ

通知一覧 / 通知設定 / マイぬい / ぬいを登録 / 配送先・お支払い / プロフィール編集。

- **通知はアプリから作らない**（設計判断2）。画面は読むだけ
- 通知設定は取引通知をオフにできない（check制約で担保済み。UIも常時オンのトグルにする）
- ぬい登録は採寸3軸を入れる。座高からサイズ区分が `sync_nui_size` で決まる

### Phase 7: 相談

メッセージ / オーダーメイド相談 / 見積り・お支払い。

- 見積りは `custom_order_quotes`。`accept_custom_quote()` で注文に落ちる
- 相談を送るとメッセージにも流す（移植元の実装がそのまま参考になる）

### Phase 8: スマホ

下部タブバーとレスポンシブ。プロトタイプのスマホ11画面が正。
