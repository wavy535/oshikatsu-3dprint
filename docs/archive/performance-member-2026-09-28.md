# 通知設定のLCP改善（2026-09-28）

> 過去の資料です。現行仕様・手順は [ドキュメント一覧](../README.md) を参照してください。計測値は記載された版・条件だけの結果です。
## 対象と結果

ユーザーから、公開サイトの「通知設定」でLCP 4.55秒、対象要素が `p.rounded-lg.bg-brand-soft.px-3.py-2.text-sm.leading-6.text-accent-foreground` と報告された。前回の[匿名ページの計測](performance-2026-09-28.md)には会員ページが含まれていなかったため、ログインした状態で `/mypage/notification-settings` を測り直した。

公開先: https://oshinest.yumaboda-official.workers.dev 。同じ計測専用会員・ブラウザ・通信条件での中央値（3回）、単位はms。

| 画面幅 | LCP 変更前 | LCP 変更後 | TTFB 変更前 → 変更後 | CLS |
| --- | --- | --- | --- | --- |
| 390px | 7140（5724〜7368） | 2484（2448〜3092） | 6722 → 2133 | 0 → 0 |
| 1365px | 6508（5496〜8860） | 2636（2220〜2696） | 6174 → 1953 | 0 → 0 |

スマホ幅で約65%、PC幅で約59%短縮。スマホでは全試行でユーザー報告と同じ要素がLCPになった。PCではページ下部の `p.text-sm.text-muted-foreground` が変更前後とも対象になった。FCPは各試行でLCPと一致し、主要内容が初回描画で表示された。通知設定の内容・操作・必須通知は変更していない。

ユーザーの4.55秒と今回の7.14秒は測定環境が異なるため、直接比較しない。また、2.48秒は3回の中央値であり、常に2.5秒以下になることや実利用者の75パーセンタイルを保証する数値ではない。変更後もTTFBが主要な待ち時間で、ネットワーク経路やWorker/D1の状態による変動が残る。

## 計測条件

- Playwright Chromium 153.0.8010.12、390×844px / 1365×844px。
- CPU 4倍減速、下り1.6Mbps、上り750Kbps、latency 150ms。
- 各試行で新しいブラウザコンテキスト、ブラウザキャッシュ無効。同じ会員セッションを設定した通常のページ読み込み。
- 各組の計測前に同じ認証状態で1回ウォームアップ。画面内リンクからの遷移時間は今回の比較対象外。
- 公開環境に計測専用の一般会員を作成。ログイン画面へのリダイレクトや非200応答は測定エラーにする。
- 計測中にビルドや他のブラウザ試験を並走させていない。重複処理の診断にはローカルの本番ビルドを用い、開発サーバーの時間は比較に含めない。
- Chrome DevTools MCPが起動できないため、既存Playwright ChromiumのCDP・PerformanceObserverで計測した。

[全15試行と条件](../performance/lcp-member-2026-09-28.json)にリソース一覧、LCP要素、TTFB、FCP、CLS、ブラウザエラーを保存した。認証情報、会員ID、メールアドレスは含めていない。計測専用会員は最後に削除し、関連セッション・認証アカウント・プロフィールの残数ゼロを確認した。

## 原因と変更

[LCPの分解](https://web.dev/articles/optimize-lcp)に沿って確認すると、説明文の装飾や画像のダウンロードではなく、HTML応答前の待ち時間が支配的だった。

まずD1への処理を整理した。

1. 認証初期化のスキーマ照合を65テーブル別々のSQLから、実際に使う5テーブルを1つのSQLで照会する形にした。実際のリモートD1で `json_each` と `pragma_table_info` の結合が使えることを確認。型・NULL・既定値の照合は維持した。
2. [Better AuthのJOIN設定](https://better-auth.com/docs/concepts/database)（1.7.3の `advanced.database.joins`）を有効にし、セッションとユーザーの読み取りをまとめた。
3. 共通ナビのプロフィールと件数取得を並行化し、通知設定で使われていなかった読み取りを削除した。

この段階のスマホLCPは7140 → 6912msにとどまり、大きな改善とは判定しなかった。

続いて本番ビルドのサーバー関数に一時的な呼び出しカウンターを置き、ブラウザのprefetchを伴わない認証済みHTTP GET 1回で確認した。ログインPOSTは別に数えた。`React.cache` を付けていたにもかかわらず、認証初期化が6回、プロフィールと共通ナビの取得が各3回実行されていた。

`getOptionalUser`・`getUserProfile`・`getShellContext` を、vinextの公開API `cacheForRequest` に変更した。[実装](https://github.com/cloudflare/vinext/blob/main/packages/vinext/src/shims/cache-for-request.ts)はHTTPリクエストのAsyncLocalStorage上でPromiseを共有する。これにより、同じGETで各処理が1回になったことをローカル本番ビルドで確認した。一時的なログは削除してから配備した。

結果はリクエスト内だけで再利用し、別のアクセスでは認証を再検証する。失効セッションの検証、ユーザーごとのDB認可、認証スキーマ照合は維持した。D1や個人情報の共有キャッシュを追加したわけではない。

JSのdecoded size中央値は前後とも541537Bで、バンドル削減による改善ではない。スマホのHTMLは51097 → 51068Bで、表示内容を削って数値を改善したものでもない。

## 配色

ユーザー指定に合わせ、主要ボタン・選択状態・フォーカスを青 `#1d4ed8` に統一した。白地と濃い文字、区切り線、小さな角丸は維持した。説明の帯に使う `#eef3fb` は補助色とし、ページ全体を淡色カードで囲う構成には戻していない。[UI設計記録](../ui-redesign.md)に反映済み。文字のコントラスト・キーボード操作・狭い画面の収まりも確認した。

## 再現

計測用会員のPlaywright storage stateはリポジトリ外・所有者のみ読めるファイルに保存する。セッションCookieを含むため、共有やGitへの追加をしない。

```bash
PERF_BASE_URL=https://oshinest.yumaboda-official.workers.dev \
PERF_STORAGE_STATE=/private/path/member-state.json \
  npm run perf:frontend -- /mypage/notification-settings

# PC幅では同じ条件に PERF_WIDTH=1365 を加える
```

公開中の既存会員を変更・削除しない。今回の片付けでは専用ファイルに記録した自作会員のID・メール・名前すべてに一致する1件だけを対象にした。
