# OshiNest を支える技術のはなし（はじめての人向け）

> この資料は2026-09-08の旧構成を説明した記録です。現在はPostgreSQL・Better Auth・S3を使い、AWS Lambdaへの配備を前提としています。現行の構成と開発手順は [README](../README.md)、変更点と検証状況は [architecture.md](architecture.md) を参照してください。

2026-09-08 時点。この資料は、パソコンやインターネットの仕組みをまったく知らない人が、
「OshiNest がどういう部品でできていて、それぞれが何をしているのか」を、
専門家と話せるくらいには分かるようになることを目指しています。
難しい言葉が出てきたら、そのつど身近なものに置き換えて説明します。

---

## 1. まず、OshiNest は何をするサービス？

「3D プリンタで作るミニチュア（推しぬい用の台座や家具）」を売り買いする場所です。

- **作る人（クリエイター）** は、3D の設計データを登録するだけ。
- **買う人** は、自分のぬいぐるみのサイズに合う作品を選んで注文するだけ。
- **運営（OshiNest）** が、印刷して、検品して、梱包して、発送します。

つまり「設計図を預かって、実物にして届ける工房つきのお店」です。

---

## 2. 全体の仕組みを「お店」に例える

Web サービスは、いくつかの「係」が分担して動いています。OshiNest の場合はこうです。

| お店に例えると | 実際の技術 | 何をしている |
|---|---|---|
| **店先（お客さんが見る画面）** | ブラウザ（Chrome など）＋ Next.js / React | 作品の一覧やカート、申請フォームなど、画面そのもの |
| **店舗の建物と店員** | AWS Amplify Hosting | 画面を作って配る。「ここに来ればお店がある」という住所（URL）を持つ |
| **倉庫と帳簿** | Supabase（PostgreSQL・Auth・Storage） | 作品・注文・ユーザー・3D データを保管し、ルールどおりに出し入れする |
| **受付（会員証の確認）** | Supabase Auth | ログイン、新規登録、SMS での本人確認 |
| **郵便屋さん** | Resend（メール）、SMS プロバイダ | 「発送しました」などの通知を届ける |
| **レジ** | Stripe（今後） | クレジットカードなどの決済。いまは開発用の「仮のレジ」で動いている |
| **目覚まし時計** | pg_cron ／ Amazon EventBridge | 「毎晩0時に期限切れを片づける」「10分おきにメールを送る」など、時間で動く仕事 |
| **設計室** | Figma | 画面のデザインを描く道具。47枚の画面設計がここにある |
| **工房** | 自作の 3D データ解析（3MF / STL） | 預かった設計図が印刷できるか検査し、材料の量や時間を見積もる |
| **金庫の鍵束** | 環境変数（.env） | 各サービスにつなぐための合言葉。コードとは別に保管する |
| **共同の作業台と履歴帳** | Git / GitHub | プログラムの変更を記録し、遡れるようにする |
| **練習用のミニチュア店舗** | Docker（ローカル Supabase） | 自分のパソコンの中に、本番そっくりの倉庫を作って試す |

図にするとこうなります。

```
 買う人・作る人・運営（ブラウザ）
              │
              ▼
   ┌───────────────────────────┐
   │ AWS Amplify Hosting        │  ← 店舗。画面を作って配る（Next.js）
   │   ＋ EventBridge（時計）    │
   └──────────┬────────────────┘
              │
   ┌──────────┴──────────┐
   ▼                     ▼
 Supabase              Resend / SMS
 （倉庫・帳簿・受付）     （郵便）
   ・データベース
   ・ログイン／本人確認
   ・3D データや画像の保管
   ・時計仕掛け（pg_cron）
                        Stripe（レジ・今後）
```

## 3. 使っている技術を一つずつ

### 3.1 画面を作る係

**Next.js（ネクスト・ジェイエス）と React（リアクト）**
画面を作るための道具です。React は「部品を組み合わせて画面を作る」考え方で、
Next.js はそれに「ページの住所」「サーバー側での組み立て」などを足したものです。
OshiNest では、画面の元になるデータを **サーバー側で組み立ててから** お客さんに送るので、
表示が速く、内部のデータが不用意にブラウザに漏れません。

**TypeScript（タイプスクリプト）**
プログラムを書く言語です。「この箱には数字しか入れない」と決められるので、
金額の欄に文字が入るような間違いを、動かす前に見つけられます。

**Tailwind CSS（テイルウィンド）**
見た目（色・余白・文字の大きさ）を指定する道具です。Figma で決めた色や余白を、
そのままの名前で使えるようにしてあります。

### 3.2 データを預かる係

**Supabase（スーパベース）**
「データベース」「ログイン」「ファイル置き場」を一式で貸してくれるサービスです。
自前でサーバーを建てなくても、倉庫と受付を最初から持てます。

- **PostgreSQL（ポストグレス）**：データベース本体。Excel の表がたくさん集まったものと思ってください。
  「作品」「注文」「印刷ジョブ」「通知」など、48 枚ほどの表があります。
- **Auth（オース）**：受付係。メールアドレスとパスワードでのログイン、
  6桁の確認コード、SMS での電話番号の確認を担当します。
- **Storage（ストレージ）**：3D データや写真の置き場。3D データは **非公開の棚** に置き、
  運営しか取り出せません。買った人にも渡りません。

**RLS（行レベルセキュリティ）**
「誰がどの行を見てよいか」を、データベース自身が判断する仕組みです。
たとえば「注文は、その注文をした本人と運営しか見られない」というルールを表ごとに書いておくと、
プログラム側で書き忘れても、データベースが勝手に隠してくれます。

**トリガーと関数**
「注文が発送されたら、買った人に通知を作る」「検品で NG になったら、注文の状態を変える」
のような **連動** を、データベースの中に仕込んであります。
プログラムは「記録を書く」だけで、あとの連動は倉庫の中で自動で起こります。
これにより、どの画面から操作しても結果が同じになります。

**マイグレーション**
倉庫の「改装記録」です。「0001 で最初の表を作った」「0015 で手数料を 20% にした」…と
番号つきで残しておき、新しい環境でも同じ順に流せば同じ倉庫ができます。いま 0001〜0026 まであります。

**pg_cron（ピージー・クロン）**
データベースの中の目覚まし時計。「毎晩 0:05 に、期限切れの見積りを片づける」のに使っています。

### 3.3 お店を建てる係

**AWS Amplify Hosting（アンプリファイ）**
Amazon が提供する「Web サイトを置く場所」です。GitHub に置いたプログラムを渡すと、
自動で組み立てて公開してくれます。

**Amazon EventBridge（イベントブリッジ）**
AWS 側の目覚まし時計。「10 分おきに、たまった通知をメールで送る」ために、
決まった URL を決まった合言葉つきで呼び出します。

### 3.4 連絡する係

**Resend（リセンド）**
メールを送るサービス。通知をメールにするときに使います。
開発中は **Mailpit** という「手元に届く偽の郵便受け」に送って、本物のメールは飛ばしません。

**SMS プロバイダ（Twilio など・本番で設定）**
クリエイター申請のときの「6桁の認証コード」を携帯に届けます。
アプリはコードを送る係を Supabase Auth に任せるので、アプリ自身は SMS 会社の鍵を持ちません。
開発中は「090-0000-0001 なら 123456 で通る」というテスト番号を使っています。

### 3.5 お金の係

**Stripe（ストライプ・今後）**
クレジットカード決済の会社です。プログラムは組んであり、鍵を入れると本物の決済に切り替わります。
いまは「即時に支払い済みにする仮のレジ」で動かしています。

### 3.6 作る係の道具

**Git（ギット）と GitHub（ギットハブ）**
Git は「プログラムの変更履歴を残す道具」、GitHub は「その履歴を置く共有の棚」です。
変更のひとかたまりを **コミット**、棚に上げることを **push（プッシュ）** と呼びます。
OshiNest のプログラムは GitHub の `oshikatsu-3dprint` に置いてあります。

**Docker（ドッカー）**
自分のパソコンの中に、本番と同じ Supabase（倉庫・受付・郵便受け）を丸ごと再現する道具です。
本番のデータを触らずに、何度でも壊して作り直せます。

**Figma（フィグマ）**
画面のデザインを描く道具。PC 36 枚・スマホ 11 枚の合計 47 画面と、色・角丸・部品の決まり
（デザインシステム）がここにあります。プログラムはこの設計図を写して作っています。

**自作の 3D データ解析**
クリエイターが登録した 3MF / STL ファイルを開き、
「穴が開いていないか」「薄すぎないか」「印刷機のベッドに載るか」を調べ、
材料の量と印刷時間から **印刷代行費** を自動で見積もります。外部の道具に頼らず自前で書いてあります。

## 4. お金の流れと、それを支える仕組み

```
買う人の支払い = 作品の価格 + 印刷代行費 + 送料
運営の手数料   = （支払い − 印刷の実費 − 送料の実費）× 20%
作る人の受取   = 支払い − 印刷の実費 − 送料の実費 − 手数料
```

- 印刷代行費は作品ごとに **3D データから自動計算** します（大きい作品ほど材料と時間がかかるため）。
- 受取額は **発送が終わった時点で実費で確定** します。それまでは見込みです。
- この計算式はデータベースの中の1か所（`order_settlements` という集計）だけが持ち、
  画面はそれを表示するだけです。画面ごとに計算がずれる事故を防ぐためです。

## 5. 安全のために決めていること

| 決めごと | 仕組み |
|---|---|
| 3D データは誰にも渡さない | 非公開の棚に保管し、運営だけが取り出せる |
| 自分で勝手に「運営」になれない | 役割を変えられるのは運営だけ、とデータベースが検査する |
| クリエイター申請には本人確認と同意が要る | SMS で電話番号を確認し、利用規約への同意を記録。どちらか欠けると申請自体が作れない |
| 番号や同意時刻は改ざんできない | 画面から送られた値ではなく、受付（Auth）と時計の値をデータベースが写す |
| 合言葉（鍵）はプログラムに書かない | 環境変数として別に保管。GitHub には上げない |
| 通知は必ず行き先を持つ | 「◯◯しました」で終わる通知を作れないように制約をかけている |

## 6. 知っておくと会話が楽になる言葉

| 言葉 | ひとことで |
|---|---|
| フロントエンド | お客さんが見て触る画面側 |
| バックエンド | 裏で計算・保管・判断をする側 |
| データベース／テーブル | 帳簿／その中の1枚の表 |
| API（エーピーアイ） | 係と係が決まった手順でやりとりする窓口 |
| 認証 | 「あなたは誰？」を確かめること（ログイン、SMS 認証） |
| セッション | ログインした状態を覚えておく仕組み |
| RLS | データベースが行ごとに「見せてよいか」を判断するルール |
| トリガー | 「◯◯が起きたら△△する」という連動 |
| マイグレーション | データベースの改装記録（番号順） |
| シード | 練習用に入れる見本データ。本番には入らない |
| 環境変数 | 合言葉や接続先を、プログラムの外に置いたもの |
| cron（クロン） | 決まった時刻に動く目覚まし時計 |
| Webhook（ウェブフック） | 外部サービスから「決済が終わった」などを知らせてもらう電話 |
| デプロイ | 作ったものを本番に置いて公開すること |
| リポジトリ | プログラムと履歴の入った棚（GitHub 上の1プロジェクト） |
| コミット／push | 変更の記録／記録を共有の棚に上げる |
| OTP（ワンタイムパスワード） | 1回だけ使える6桁の確認コード |
| E.164 | 電話番号の国際表記（090-… → +8190…） |

## 7. これから使う予定のもの

- **Stripe**：鍵を入れて本物の決済に切り替える。
- **SMS プロバイダ**：Supabase の管理画面で Twilio などを設定する（アプリの変更は不要）。
- **EventBridge**：本番で通知メールを 10 分おきに送る配線。
- **プリンタ管理**：運営コンソールの残り画面（指示により最後に着手）。
- **スマホ向けの仕上げ**：Figma のスマホ 11 画面に合わせた調整。

---

## 8. 開発の進め方（ざっくり）

1. **手元で作る**：Docker で練習用の Supabase を立て、`npm run dev` で画面を動かして確認する。
2. **記録する**：ひとまとまりごとにコミットし、GitHub に push する。
3. **本番に出す**：Amplify Hosting が GitHub から自動で組み立てて公開する。
   データベースの改装は `supabase db push` で番号順に流す。

「手元で壊しても本番は無事」「履歴があるからいつでも戻れる」の2つが、安心して進められる理由です。
