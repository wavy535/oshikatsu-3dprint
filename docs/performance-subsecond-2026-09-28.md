## 原因と採用した変更

### D1とWorkerの距離

Smart Placementは `INSUFFICIENT_INVOCATIONS` のままで、自動配置が働いていなかった。D1の実際のprimaryはSINであり、複数のDB往復が遠距離になっていた。

`wrangler.jsonc` に `placement.region = "aws:ap-southeast-1"` を指定。これは[Cloudflareの配置ヒント](https://developers.cloudflare.com/workers/configuration/placement/)で、AWSリソースを作ったり使ったりする設定ではない。D1のデータ移行は行わず、静的assetsは入口のエッジから配信する。

配置後の診断では、D1の各往復は主に10〜23ms、SQL実行は0.3〜7ms。最終構成の別の診断3件ではWorker全体のwall timeは110〜152ms、CPUは37〜78msだった。これらは個別診断であり、最終LCP試行と同一リクエストの内訳ではない。

セッションのDB検証・失効確認、認証のスキーマ照合、利用者ごとの認可を維持。別リクエストへの認証キャッシュは追加していない。一時的なD1診断ログは公開コードから削除済み。

### 最初のHTMLに必要なCSSを含める

vinextがサポートする `experimental.inlineCss` で、初回描画の別CSS往復をなくした。ただし全CSSを含めるだけではHTMLが大きくなり、通知設定はまだ中央値1192msだった。

ビルド後に `beasties@0.5.4` のcompilerでCSSを解析し、プランだけをWorkerへ組み込む。実行時にはそのHTMLのDOMで使う規則を抽出する。compilerやPostCSSはWorkerに入れず、HTML・認証情報・DOM形状の共有キャッシュも持たない。新しいコンポーネントや画面遷移のための完全なCSS読み込みは残す。

抽出前のHTMLを256KiBまでに制限し、超過時は読み取った部分を欠損なく戻して元のストリームを継続する。GETの成功HTMLだけが対象で、API、RSC、Server Action、ファイル配信には適用しない。抽出に失敗した場合は元の完全CSSで表示する。

抽出器には2点の補正が必要だった。

- leaf block at-ruleの末尾に付く余分な `;` で、次の `@property` がブラウザに捨てられた。これを除き、罫線を維持した。
- `:where(select, textarea)` などの単独擬似クラスが正規化で落ちるため、これらの小さいグローバル規則は保持した。

JavaScript無効のスマホ・PCで、6画面の全要素のレイアウト・色・罫線・文字を、完全CSSに差し替えた同じDOMと比較した。ネイティブの折りたたみメニューを開いた状態も確認。依存更新時はこの試験を維持する。

HTTPの `Link` ヘッダーに残っていた全CSSの先読みも除いた。最初のHTMLとの帯域競合を防ぎ、CSS以外のヒントは保持する。

### 圧縮をブラウザまで維持する

小さいHTMLだけをまとめてBrotli quality 6で圧縮。`cf.clientAcceptEncoding` にBrotli対応がない場合は通常配信へ戻す。圧縮失敗時も通常配信を続ける。実環境でBrotli対応、gzipのみ、identityの表示を確認した。

交渉の制約として、公開エッジが `gzip, br;q=0` を `gzip, br` に変換してWorkerへ渡すケースを確認した。実装はq値が届けば0を拒否するが、失われたq値は復元できないため、特殊なq指定まで厳密に尊重できるとはしていない。Brotli自体を提示しないクライアントにはBrotliを返さない。

`encodeBody: "manual"` だけではエッジでZstandardに再圧縮されていた。圧縮済み応答に `Cache-Control: no-transform` を付けて、[再圧縮を防止](https://developers.cloudflare.com/rules/compression-rules/)した。これはキャッシュ保存期間を増やす指定ではなく、既存のキャッシュ制御を保持する。`Vary: Accept-Encoding` も追加。

最終版のHTML転送量中央値はトップ約10.7KB、作品一覧約11.5KB、通知設定約11.7KB。全文CSSを含めた段階の通知設定は約17.8KBだった。圧縮は[Workersのネイティブzlib](https://developers.cloudflare.com/workers/runtime-apis/nodejs/zlib/)を使う。

## 見送った変更と中間結果

- 配置変更だけでは通知設定1276ms、全文CSSをインライン化しても1192ms。どちらの段階も1秒達成とは判定しなかった。
- 必要CSSだけを抽出した段階は1048ms、重複preload除去後は1156ms。通信変動があるため、小さい中央値差を単独の改善効果として断定しない。
- HTMLをまとめて送るだけでは1068msで、目標未達。Brotliの適用後もエッジで再圧縮されることを実レスポンスで確認し、配信まで修正した。
- 文章の折り返し変更と、画面外への `content-visibility` は、小さな同一HTML比較で明確なレイアウト短縮が見えず不採用。文言・内容を削ったり、LCP対象を隠したりしていない。

## ビルドと再計測

本番ビルドは必ず `npm run build` を使う。Viteの後に `scripts/build-critical-css.mjs` が、生成されたCSSをサーバーのエントリに組み込む。`vite build` 単独ではこの工程を実行しない。プランがない開発実行では通常のvinextレスポンスを返す。

```bash
npm run build
npm run preview -- --port 3000

# stateには認証Cookieが含まれる。リポジトリ外・所有者のみ読める場所へ保存する。
PERF_BASE_URL=https://oshinest.yumaboda-official.workers.dev \
PERF_STORAGE_STATE=/private/path/member-state.json \
  npm run perf:frontend -- / /works /mypage /mypage/notification-settings /mypage/orders /cart

# 未ログインはPERF_STORAGE_STATEを指定しない
PERF_BASE_URL=https://oshinest.yumaboda-official.workers.dev \
  npm run perf:frontend -- / /works /login

PERF_BASE_URL=https://oshinest.yumaboda-official.workers.dev \
PERF_STORAGE_STATE=/private/path/member-state.json \
  npm run perf:navigation
```
