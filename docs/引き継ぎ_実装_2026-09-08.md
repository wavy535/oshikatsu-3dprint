## 2. このセッションでやったこと

1. **Phase 0**: ローカルDBを初めて立ち上げ（0001〜0010を適用）、型を `supabase gen types` の
   生成物へ差し替え、開発シードとダミー画像スクリプトを追加
2. **Phase 1**: デザイントークン、共通シェル、ルートグループ、権限ガード、
   ログイン・新規登録（**メール＋パスワード2回 → 6桁の確認コード**）
3. **Phase 2**: 一覧・検索（絞り込み／並べ替え／マイぬいサイズ既定）、作品詳細
   （サイズ選択で価格と**相性判定**が変わる）、お気に入り、カート
4. **マイページ系**: マイぬい／お気に入り一覧／通知・通知設定／配送先／
   購入履歴・注文詳細・**受け取り評価の2段**
5. **出品フロー**: 作品管理と4STEP（3Dデータの自動検証 → 印刷指示 → 作品情報 → 公開）
6. **運営コンソール**: 印刷キュー → ジョブ詳細 → 検品・発送登録の3画面（下の「運営コンソール」節）
7. **運営コンソールの残り**: 注文一覧・注文詳細、出荷済み、フィラメント在庫（補充・廃棄・追加）、売上・手数料。
   あわせて**手数料を 20% に**、**送料を注文に持つ**ように変更（0015）、
   **精算を実費で行う**ようにした（0016・下の「お金の出し方」）
8. **決済**（0017）: `place_order()` / `confirm_order_payment()` / `cancel_unpaid_order()` を DB に置き、
   Stripe Checkout（キーがあるとき）と開発用の即時確定を同じ経路に乗せた。販売通知は支払い済みで出す
9. **修正依頼**（0018）: クリエイターが検品NGを受けて対応（データ差し替え／指示変更／出品停止／運営に相談）
10. **売上ダッシュボードと払込**（0019）: 明細ごとの精算ビュー、受取残高ビュー、振込申請と運営の処理
11. **相談系**（0020）: メッセージ、オーダーメイド相談 → 見積り → 承認 → 専用サイズがカートへ → 決済
12. **公開プロフィール・レビュー・Q&A**（0021）: フォロー、数字は definer 関数、Q&A の通知
13. 実績の修正（履歴つき）、`scripts/verify-0014-0021.sql`、ページタイトル、ID検査の緩和

## 3. 次にやること

### A. 運営コンソール（このセッションで実装済み）

`/admin/print-queue` → `/admin/print-queue/[id]`（ジョブ詳細）→ `/admin/print-queue/[id]/qc`
（検品・発送登録）の3画面が動きます。**印刷開始 → 実績記録 → 検品NG（モデル側）→ 修正依頼 →
再印刷 → 検品OK → 発送登録 → 購入者の注文が「発送済み」** まで実機で通してあります。

- 検品項目は `qc_check_definitions` から読む（画面にベタ書きしない）
- ジョブのステータスも修正依頼も注文ステータスもDBのトリガーが決める。
  アプリが書くのは `print_jobs` の実績・`qc_inspections` / `qc_check_results`・`shipments` だけ
- 実使用グラムを入れると `filament_ledger` に消費が積まれ、`filaments.stock_grams` が減る
- 検品写真は `qc-photos`（非公開バケット・0014で追加）。パスは `{work_id}/{print_job_id}/{ファイル名}`。
  NG が「モデル側」なら写真ごと修正依頼に渡る

同日に **注文一覧（`/admin/orders`・`/admin/orders/[id]`）／出荷済み（`/admin/shipments`）／
フィラメント在庫（`/admin/filaments`）／売上・手数料（`/admin/sales`）** も追加済み。
残っているのは **プリンタ管理** だけ（ナビには出しているが押せない見た目）。

- 注文一覧は導出されたステータスを出すだけ。進めるのはジョブ（印刷キュー）と発送登録
- フィラメント在庫は数字を直接書かず、補充・廃棄・調整を `filament_ledger` に積む
  （`stock_grams` はトリガーが更新）。「予定消費」は作業中ジョブの推定グラムを代表スロットの
  素材・色で束ねたもの。残りわずかの目安は `LOW_STOCK_GRAMS`（labels.ts）
- 売上・手数料は注文時のスナップショット（`orders` / `order_items` の `*_amount`）を足すだけ。
  料率を掛け直さない（料率を変えても過去の注文が動かないように）

## 4. 触るときに知っておくこと

### お金の出し方（重要）

`print_pricing_rules.fee_billing` は **`separate`**（印刷代行費は作品価格に**上乗せ**して請求）。
**金額を画面に出すときは必ず `work_variant_pricing` を見ること。**

- `buyer_total_jpy` … 買う人が払う額（= `price_jpy` + `print_fee_jpy`）
- `creator_payout_jpy` … クリエイターの受取額
- `min_price_jpy` … 価格の下限（separate なら100円）
- 一覧の表示・並べ替え用に `works.min_buyer_total_jpy`（0013で追加）

`works.min_price_jpy` は**クリエイター価格側**の最小値で、値下げ通知の基準にも使われています。
これをそのままカードに出すと安く見えるので注意。

**手数料の決め（2026-09-08・運営の指示）**

> 印刷にかかった金額（実費）と送料（実費）を売れた金額から引いて、その残りに 20% の手数料

- 購入者の支払い（`orders.total_amount`）= 作品代金（`subtotal_amount`）+ 印刷代行費
  （`print_cost_amount`）+ 送料（`shipping_fee_amount`・0015で追加）
- **精算は実費で行う（0016）**。式は `order_settlements` ビューだけが持つ:
  `差引 = 支払い − 印刷の実費 − 送料の実費`、`手数料 = 差引 × 料率`、`受取 = 残り`。
  印刷の実費は `order_actual_print_cost()`（実使用グラム × 使ったフィラメントの単価 ＋
  実印刷時間 × 機械費 ＋ 検品梱包）、送料の実費は `shipments.shipping_fee_jpy`
- 実費は**発送が終わると確定**（`is_final`）。それまでは請求した代行費と購入者負担の送料で
  **見込み**を出す。売上画面・運営の注文詳細は確定／見込みのバッジで区別している
- 出品時にクリエイターへ見せる受取額（`work_variant_pricing.creator_payout_jpy`・STEP3）は
  見込みのまま（代行費 ＝ 実費の見込みなので 作品代金 × 80% になる）。
  **実費との差は 80/20 でクリエイターと運営が分け合う**形になる。
  「差はすべて運営が持ち、クリエイターは常に作品代金 × 80%」にしたければ、
  ビューの `pool_amount` を `goods_amount` に置き換えるだけで済む
- 料率は `print_pricing_rules.platform_fee_rate`（0015 で 0.10 → 0.20）。
  注文ごとに `orders.platform_fee_rate` へ写す（トリガー）ので、**料率を変えても過去の注文は動かない**
- 差引がマイナスの注文は手数料 0・受取マイナスになる。売上画面で赤く出るので運用で判断する
- `orders.shipping_fee_amount`（購入者が払った送料）と `shipments.shipping_fee_jpy`
  （運営が配送業者に払った実費）は別物。出荷済み一覧は両方を並べて出す
- 決済を作るときは `shipping_fee_amount` を確定して `total_amount` に足すこと（シードは一律 520 円）

### 計算はDBに寄せる

代行費 `calc_print_fee` / 重量 `estimate_filament_grams` / 相性 `nui_fit_axes`・`nui_fit_verdict` /
人気順 `popular_works` / 未読数 `unread_notification_count` / 注文ステータス `sync_order_from_jobs` /
内寸のスケール `scale_fit_dims`。**アプリ側で同じ計算を書かないこと。**

内寸だけは注意点があります。`scale_fit_dims` は「自分が値を持っていたら触らない」ので、
原寸を変えたときに他サイズへ反映するには **一度 null に戻してから `scale_ratio` を書き直す**
必要があります（`step-actions.ts` の `saveWorkInfoAction` にその処理があります）。

### RLS の黙った失敗

- **更新系は必ず `.select()` を付けて更新行数を見る**。ポリシーが無いと
  エラーにならず0行更新になり、成功したように見えます。
- **ビューを作ったら `security_invoker = on`**。付け忘れると所有者権限で動き、
  下敷きテーブルのポリシーが効きません。
- **トリガー関数は「誰が操作したとき、どのテーブルへ書くか」で判定**。
  持ち主以外の行へ書くなら `security definer` が要ります。
  棚卸しは `select proname, prosecdef from pg_proc where prorettype='trigger'::regtype`。

### ファイルのアップロード

3Dデータと画像は**ブラウザから Storage へ直接**上げます（Server Action の本文サイズ制限のため）。
パスは storage のポリシーに合わせて `{ユーザーID}/{作品ID}/{ファイル名}`。
アップロード後の登録は、**FormData を組んで Server Action へ直接渡す**こと。
隠しフォームに値を入れて `requestSubmit()` する形は、値が反映される前に送信されて
**素通りします**（実際に踏みました）。

### 構成の約束

- ドメインのロジックは `src/lib/<ドメイン>/{queries,actions}.ts`（`src/features/` は作らない）
- `"server-only"` なモジュールから型や定数をクライアントに渡さない。
  共有するものは別ファイルへ（例: `src/lib/works/list-options.ts`）
- 型は `src/types/db.ts` 経由で参照する。`database.ts` は `gen types` が丸ごと上書きします
- Tailwind の**任意値クラスが生成されないことがある**（`lg:w-[320px]` で崩れた）。
  標準スケール（`lg:w-80`）を使うのが安全

### お金の流れ（クリエイター側）

- 明細ごとの精算は `creator_item_settlements`、受取残高は `creator_payout_balances`（0019）。
  受取可能額 = 確定受取（発送済み・取引完了） − 再印刷の負担 − 申請中・振込済み
- 振込申請は全額。残高の範囲内・¥1,000 以上・口座登録済みを**DB のトリガーが検査**する（画面の検査に頼らない）
- クリエイターが自分の作品の入った注文・発送記録・ジョブを読める（0018/0019）。
  `orders` ↔ `order_items` のポリシーが相互参照して無限再帰になるので、判定は definer 関数（`order_has_creator_items`）

### オーダーメイドの決まり

- 承認（`accept_custom_quote`）で**購入者専用のサイズ**（`is_listed = false`・在庫1）ができてカートに入る。
  他人には見えず、本人だけが買える（`variant_reserved_for`）。`place_order` もこれを見て通す
- 注文確定で見積りは `ordered` に。承認・辞退・注文はクリエイターに通知（トリガー）
- 見積りの印刷代行費は `calc_print_fee`、送料は料金表。有効期限 7 日

### 相談系・公開プロフィール

- メッセージは相手ごとのスレッド（`?with=<userId>`、`with=admin` は運営）。開いたら既読
- フォローは公開情報（誰でも数えられる）。公開プロフィールの数字は `creator_public_stats()`（definer）
- Q&A は公開。回答は作品のクリエイターだけ（RLS）。質問・回答は通知（トリガー）

### ID の検査

zod の `uuid()` は RFC 4122 の版・変異体まで見るので、開発シードの固定ID（`22222222-2222-…`）を弾く。
ユーザーIDを受ける入力は `src/lib/validation.ts` の `idSchema`（uuid 型が受ける形までの検査）を使う。

### 運営コンソールを触るとき

- 画面が書いていいのは **`print_jobs` の実績・プリンタ・ステータス**、
  **`qc_inspections` / `qc_check_results`**、**`shipments`**、**`filament_ledger`** だけ。
  注文ステータス（設計判断9）・修正依頼（設計判断7）・通知（設計判断2）はDBが決める
- ジョブの遷移は `src/lib/ops/actions.ts` の `updateJob()` を通す。
  遷移元のステータスを `allowedFrom` で確かめてから更新し、`.select()` で行数も見ている
- 一覧に列を足したくなったら **`print_queue` ビュー側に足す**（アプリで join を組み直さない）。
  素材・色が「代表スロット = `slot_index` が最小」という決めはビューが持っている
- ラベル（ステータス名・原因・配送業者）は `src/lib/ops/labels.ts`。
  クライアントコンポーネントからも読むので `server-only` な queries.ts には置かない

### 検証のやり方

毎回この順でやっています。**画面表示だけで完了とみなさない**こと。

1. `npx tsc --noEmit` / `npm run lint` / `npm run build`
2. ブラウザで**その操作そのもの**を実行する
3. `docker exec supabase_db_osinest psql -U postgres -d postgres -c "..."` で実データを確認

ブラウザ自動化には癖があります（[[osinest-local-dev]] のメモにも書いてあります）。
`computer` の type/click が数回に1回効かないので、フォームは JS の native setter で入れて
`click()` する方が確実です。`document.querySelector('button[type=submit]')` は
**ヘッダーの検索ボタンを掴む**ので、対象フォームを特定してから押してください。

### メールと定期実行

- 環境変数: `CRON_SECRET`（無いと `/api/cron/*` は 503）、`RESEND_API_KEY`、`MAIL_FROM`
  （`"OshiNest <no-reply@example.com>"` 形式）。開発では `MAILPIT_URL`（既定 `http://127.0.0.1:54424`）
- 手で送るとき:
  `curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/dispatch-emails`
  → `{"provider":"mailpit","sent":6,"notified":6,"deferred":0,"failed":0,"errors":[]}` のような JSON。
  `deferred` はまとめ受信の時刻でないため今回は送らなかった件数
- 本番の cron は EventBridge（スケジュールルール → API Destination。Connection に `Authorization: Bearer <CRON_SECRET>` を持たせる）か、
  pg_cron + pg_net でこの URL を叩く。どちらでも良いが**5〜10分おき**が目安
- メールの文面は `src/lib/mail/dispatch.ts` の `buildMail()` 1か所。件名は
  1件なら通知のタイトル、複数なら「新しい通知が N 件あります」
- 通知の `kind` ごとのメール ON/OFF は `notification_preferences.email`。行が無ければ ON。
  まとめ受信（daily）の設定画面はまだ無い（DB の `notification_settings` を直接書けば効く）
