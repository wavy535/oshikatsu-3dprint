# 全体の問題点と改善状況

2026-09-09。`refactoring`ブランチでの診断と実装状況。現在の対象はAWSで動くデモ環境で、実課金は不要。アプリ内通知とメール配信は残す。

## 現在の構成

Next.jsのServer Components / Server Actionsと機能別の `src/lib/*` を基本にする。取得・変更は機能別のqueries/actionsに置く。複数テーブルの変更は既存のKyselyトランザクションでまとめ、注文確定など既存のDB関数は維持する。Repository、DIコンテナ、機能ごとのサービス層は一律に追加しない。

低利用の学習用途に合わせ、AWS LambdaのNode.jsコンテナ内でNext.jsとBetter Authを実行する構成例へ変更した。Lambda Web Adapterを使い、DBはAurora Serverless v2の0 ACUへの自動停止を設定する。ファイルはS3、メールはSES、電話番号認証はSNS。[配備構成と設定例](../infra/aws/README.md)を参照。AWS上での配備・復帰動作はまだ未検証。

運営の処理は `src/lib/ops/` 内の印刷・注文・発送・在庫・売上・メンバー管理に分割し、画面から必要なモジュールを直接参照する。共通の仲介層や再export用のファイルは置かない。

## ページングと取得の方針

通常の一覧は共通の `readPage` で表示件数より1件多く読み、次ページの有無を判定する。件数の表示が不要な一覧にはCOUNTを増やさない。作品検索は既存の24件と総件数の取得を維持し、ページ番号を全件分生成する処理を前・次の固定数リンクへ変更した。払込履歴と再印刷費用はそれぞれ独立してページを移動できる。

合計や平均は表示ページに依存しないSQL集計、画面内だけの件数は「このページ」と表示する。メッセージは途中の新着で過去ページがずれないよう `(created_at, id)` で比較する。カーソルにはメッセージIDを使い、DB内で時刻を解決してPostgreSQLのマイクロ秒精度を保持する。

Server ComponentsからKyselyで直接取得し、同じリクエスト中の重複はReact.cacheで共用する。利用者の情報を別リクエストへ持ち越すキャッシュは追加しない。作品カード・履歴の行リンク・ページ切り替えには `prefetch={false}` を明示し、先読みでDBを起こす機会を抑える。作品カードの画像は最初の4枚を通常読み込み、残りを遅延読み込みにする。定期fetchや別のキャッシュ基盤は不要。

同じローカルDB・購入者セッションで、変更前の `9979ade` と変更後の本番コンテナを比較した。Lambda用の接続設定で、1回のHTML取得中にpg.Clientが実行する問い合わせを数えた値。認証・プロフィールの問い合わせを含み、接続時のロール設定・トランザクション制御を除く。ブラウザの追加リクエストや画像取得は含めない。

| 画面 | 変更前 | 変更後 |
| --- | ---: | ---: |
| 作品一覧 | 12回 | 7回 |
| 作品詳細 | 18回 | 10回 |
| 購入履歴 | 10回 | 5回 |
| クリエイターのレビュータブ | 13回 | 9回 |

これは問い合わせ数の比較で、AWSでの応答時間や費用の実測ではない。通常一覧はOFFSET方式なので深いページの走査量は増える。履歴が大規模になったら、その一覧もカーソル方式へ変更する。今回の学習用途では全画面に複雑なカーソル管理を導入しない。

## 3D解析の負荷と対応範囲

[上限の定義](../src/lib/print/limits.ts)をアップロード・パーサ・解析で共用する。3MFはZIPの申告サイズに加えて、zlibの `maxOutputLength` で実際の展開量を制限する（[Node.jsの仕様](https://nodejs.org/api/zlib.html#class-options)）。チェックサム・破損した範囲・不正な頂点参照・部品の循環も検査し、途中まで読めたモデルを成功扱いしない。ZIP64・分割ZIP・暗号化ZIPは対象外。

形状の広がりでグリッドへの登録数が膨らむため、割り当て前に400万参照で止める。厚みと自己交差はそれぞれ最大3,000面・4,000面をサンプリングし、全パーツ合計5,000万候補の探索上限を共有する。上限に達した場合は解析エラーとして、面数の削減・パーツの分割を案内する。追加の常駐プロセスやジョブ基盤は導入しない。

10秒の期限はループの区切りで確認する協調的なもの。同期処理を強制中断する仕組みではなく、ZIPの展開や個々の処理区間が期限を越える可能性はある。入力・展開量・要素数・探索回数の上限も併用する。S3ダウンロードは別に30秒の期限と実際の受信バイト数の検査を持つ。

同じ合成トーラスのバイナリSTLを、変更前の `52bfc4f` と変更後のNode.js 24で比較した。各ケースを独立したプロセス・640MiBのJSヒープ上限で1回ずつ実行。時間は解析部分、最大RSSはモデル生成を含むプロセス全体であり、AWSの実測や上限メモリの保証ではない。

| 面数 | 時間（前 → 後） | 最大RSS（前 → 後） |
| --- | ---: | ---: |
| 51,200 | 403 → 312ms | 147 → 126MiB |
| 199,712 | 1,548 → 1,054ms | 338 → 308MiB |
| 500,000 | 3,829 → 2,444ms | 538 → 490MiB |

体積と閉じたメッシュの判定は維持。サンプル数を上限内に直したため、厚み・交差の近似値が以前と完全一致する保証はない。再計測は `npm run benchmark:print -- 160`（または316・500）、実ファイルは `npm run analyze -- <path>` で行う。肉厚や自己交差の検査は印刷可否の補助であり、全ての不具合を検出するものではない。

## ARプレビュー（実寸表示）

作品詳細のサイズ選択の下に「ARで実寸を見る」を置く。[model-viewer](https://modelviewer.dev/)（Apache-2.0）が端末に合わせて Quick Look（iPhone の Safari）か WebXR / Scene Viewer（Android）を選び、拡大縮小を禁止して実寸で置く。本物のぬいは画面上で部屋と重ならない位置に並べて見る前提で、遮蔽や写真の合成はしない。

- 作品：[`/api/ar/works/[workId]/[variantId].glb`](../src/app/api/ar/works/[workId]/[file]/route.ts) が、サイズに紐づく3Dデータ（なければ主データ）をS3から読み、既存のパーサで読んでGLBにする。`scale_ratio` をかけ、三角形は[設定](../src/lib/ar/config.ts)の上限まで頂点クラスタリングで間引く。色は反映せず単色、複数パーツの3MFは印刷用に並べた配置のまま表示する
- 仮の部屋：[`/api/ar/rooms/{three-walls|back-left}.glb`](../src/app/api/ar/rooms/[file]/route.ts) が、メインのマイぬいの採寸値（URLで受け取る）から床・壁（3面／奥と左の2面）・透明な天井・ぬいの目安の箱を作る。DBは読まない。目安の箱は相性判定と同じく幅・奥行きに抱き幅（なければ肩幅）、高さに座高を使う。余白・厚みは仕様が決まっていない仮の値

仮の部屋は `.usdz` でも返す。Quick Look は USDZ の URL を直接開けるので、`#allowsContentScaling=0` を付けたリンクなら実寸固定のままARを起動できる。USDZは無圧縮ZIPで各ファイルを64バイト境界に置き、USDAの構成は three.js の USDZExporter に合わせた。開発環境専用の [`/dev/ar`](../src/app/dev/ar/page.tsx) は、入力した寸法からこのリンクのQRコードを作る（localhost で開いてもLANアドレスを入れる。本番は404で、DBとログインは使わない）。

3Dデータの公開方針を変えた。これまで3Dデータはどの公開ルートからも返していなかった（公開ルートは画像のみ）。Scene Viewer は未ログインでモデルのURLを取りに来るため、公開中の作品・掲載中のサイズに限り、AR用のGLBを公開のGETで返す。返すのは間引いた単色の形状で印刷用の元データではないが、形状自体は取り出せる。仮の部屋の生成と作品データの変換の両方に対応すると決めたこと（2026-09）による。URLの `v` は保存先のハッシュで、3Dデータを差し替えると古いURLは404になる。

未検証・制約：iPhone / Android の実機でのAR表示と実寸のずれは未検証（生成したGLBはKhronos glTF Validatorでエラー・警告0件、USDZは `unzip -t` でエラーなし）。iOSのSafari以外（Chrome・アプリ内ブラウザ）では model-viewer がUSDZを作らずARボタンが出ない。Scene Viewer では model-viewer が遮蔽を無効にする。変換はリクエストごとに行い、キャッシュは公開の Cache-Control だけでS3には保存しない。

## 次に改善する対象

### 残る一覧の取得上限・エラー処理

増え続ける主要一覧はページング済み。運営のクリエイター別売上は1クリエイター1行の集計値だが、クリエイター数の上限はまだない。プリンタ・材料・運営メンバー・配送先など、少数を選択・管理する一覧は全件取得を維持している。DB内の全体集計やメッセージのスレッド集約もデータ量に応じた計算は必要で、LIMITだけでその計算がなくなるわけではない。一部の取得処理には、DBエラーを空配列・0に置き換える箇所も残る。

### 3D形式の対応範囲

[registerAssetAction](../src/lib/works/step-actions.ts)は解析不能なファイルへの差し替えを保存前に拒否する。形状解析まで完了した場合は、検証結果がNGでもその診断結果を保存・表示する。DBは複数・サイズ別アセットを表せる一方、現在のUIは1作品1データ。複数データ対応を増やす際は、指示・サイズ展開の対応範囲も揃える。

[ZIP処理](../src/lib/print/zip.ts)と[3MF XML処理](../src/lib/print/threemf.ts)の対応範囲は限定的。属性の一重引用符と空白には対応したが、モデルは `3D/3dmodel.model` を読む構成のままで、外部モデル参照・OPCの関係定義・任意の名前空間などの汎用対応は残る。複数のエクスポータの実ファイルで検証し、必要になった範囲で保守されているパーサへの置換を比較する。

3Dの幾何計算自体はアプリ固有の処理として維持する。大量同時アップロードの負荷と、モデルの種類による最大メモリは未検証。S3に残る差し替え前・解析失敗のファイルの整理方法も、保存期間を決めてから扱う。
