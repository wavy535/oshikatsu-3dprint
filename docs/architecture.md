# 全体の問題点と改善状況

2026-09-09。`refactoring`ブランチでの診断と実装状況。現在の対象はAWSで動くデモ環境で、実課金は不要。アプリ内通知とメール配信は残す。

## 現在の構成

Next.jsのServer Components / Server Actionsと機能別の `src/lib/*` を基本にする。取得・変更は機能別のqueries/actionsに置く。複数テーブルの変更は既存のKyselyトランザクションでまとめ、注文確定など既存のDB関数は維持する。Repository、DIコンテナ、機能ごとのサービス層は一律に追加しない。

低利用の学習用途に合わせ、AWS LambdaのNode.jsコンテナ内でNext.jsとBetter Authを実行する構成例へ変更した。Lambda Web Adapterを使い、DBはAurora Serverless v2の0 ACUへの自動停止を設定する。ファイルはS3、メールはSES、電話番号認証はSNS。[配備構成と設定例](../infra/aws/README.md)を参照。AWS上での配備・復帰動作はまだ未検証。

運営の処理は `src/lib/ops/` 内の印刷・注文・発送・在庫・売上・メンバー管理に分割し、画面から必要なモジュールを直接参照する。共通の仲介層や再export用のファイルは置かない。

通知メールは通常の同時実行による重複を避けるが、SES受理直後にDBへの記録が失敗した場合などは再送され得る。7日を超える通知を送信対象から外す既存仕様も維持している。完全な一回配信や無期限の再試行は保証しない。

## 次に改善する対象

### 残る一覧の取得上限・エラー処理

作品検索と売上の全件読み込みは対応済み。運営のクリエイター別一覧は1クリエイター1行の集計値だが、クリエイター数の上限はまだない。払込申請や一部の運営一覧にも全件取得が残るため、実際の件数と用途に合わせてページングする。売上以外の取得処理には、DBエラーを空配列・0に置き換える箇所も残っている。

### 3Dデータの差し替え

[registerAssetAction](../src/lib/works/step-actions.ts)の登録は、実ファイルを確認してから削除・挿入を同じトランザクションで行うよう変更した。ただし解析は登録後なので、新データの解析失敗時にも旧データへ戻れるようにする余地がある。DBは複数・サイズ別アセットを表せる一方、現在のUIは1作品1データなので、その対応範囲も揃える。

### 3MFの汎用処理と解析の上限

[ZIP処理](../src/lib/print/zip.ts)と[3MF XML処理](../src/lib/print/threemf.ts)を自作している。展開後サイズの明示的な上限がなく、属性は二重引用符専用、モデルファイルのパスも固定。代表ファイル・境界入力・処理時間・メモリを確認して、保守されている汎用実装との置換を比較する。

3Dの幾何計算自体はアプリ固有の処理として維持する。HTTPリクエスト内の同期解析について、入力・展開サイズ・計算量の上限と計測を先に整える。必要性が分かる前から別ワーカーやジョブ基盤を増やさない。
