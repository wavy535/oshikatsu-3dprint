# 全体の問題点と簡素化の計画

2026-09-08。コード・依存関係・ローカルDBの全体診断と、`refactoring` ブランチでの改善記録。実装済み機能を維持する前提で進め、機能の廃止が必要な案には条件を付けている。

## このブランチで対応したこと

| 対象 | 実装・検証 |
| --- | --- |
| RPCと通知の認可 | 0027・0028で匿名操作と通知内部関数の公開実行を制限。購入者・別ユーザー・運営・サービスのDBロールで検証 |
| アセットの再解析 | 作品とアセットの所属を利用者権限で確認し、解析側も認可済み作品に限定。旧Actionを削除。修正前に失敗するテストから修正を確認 |
| 決済 | 0029で注文とSessionを記録し、金額・通貨・状態の照合と更新を一つのDB操作にした。Webhook失敗は500。完了表示・戻るURLから更新を除き、本人確認するActionで照会・再開・取消を行う |
| 開発用決済 | 開発環境かつ明示設定の場合だけ許可。本番やWebhook設定不足では注文作成前に止める。開始済みのStripe決済を開発決済へ切り替えない |
| 不要な依存・検証経路 | 未使用の直接依存6件を削除。Vitest、設定例、Node.jsで動く解析スクリプトと四面体の検証データを追加 |
| 同一リクエストの取得 | Reactのリクエスト内キャッシュで認証とプロフィールを共用。管理レイアウト・ヘッダーのプロフィール取得、購入画面での価格再取得を削減。カート・価格・送料の取得失敗を0円にしない |
| 按分・概算 | 0030のSQLを運営・クリエイター・残高で共用。累積比率の差で端数を配り、複数クリエイター・少額・負の精算でも合計を保存。個別見積りも既存の印刷費関数を使い、基本作業料を含める |

決済の自動再試行は同じ冪等キー・注文スナップショットを使う。[Stripeの冪等キーは24時間以降に削除され得る](https://docs.stripe.com/api/idempotent_requests)ため、Sessionを保存できず結果不明のまま23時間以上経過した場合は自動再送を止め、運営への問い合わせを案内する。既に保存済みのSessionは再取得できる。

**次の対象**は、検索・売上の1,000件上限対策とDB集計、作品・運営の保存のトランザクション化、メールの処理中と送信済みの分離。旧課金方式・保留機能の廃止、ZIP/XMLの置換はまだ行っていない。

以下は診断時点の根拠を残したもの。対応状況は上の表を優先する。

## 診断結果

機能別の `src/lib/*`、Server Actions、Supabaseという基本構成は比較的素直。削減効果が大きいのは、未使用の依存、過去・将来の仕様を抱えた分岐、同じデータの繰り返し取得、SQLとTypeScriptに重複した業務計算である。ZIP/XMLの汎用処理を自作している部分にも保守負担がある。

一方、認可・決済・複数テーブル更新には境界の不足がある。コードを減らす作業と、正しさを保証する作業の両方が必要。**全機能へのサービス層追加や、ファイル数を増やすこと自体は目標にしない。** 前版のサービス層を中心とした構成図と、運営機能を6ディレクトリへ一律に分ける案は取り下げる。

確認範囲は、アプリ・UI部品・機能別ライブラリのimportとDB参照、依存パッケージと設定、マイグレーション、ローカルDB、検証スクリプト、READMEと引き継ぎ資料。診断時点（0028適用後）のpublicスキーマは49テーブル・10ビュー・68関数・40トリガー・97 RLSポリシーだった。関数数はトリガー関数も含む。この数自体を過剰設計の根拠にはしない。

## 機能を維持しながら減らせるもの

### 1. 未使用の依存6件と、使われなくなったAction（小）

[package.json](../package.json) の次の直接依存は、アプリ・スクリプト・設定からの利用を確認できなかった。

- `@hookform/resolvers`、`react-hook-form`
- `@radix-ui/react-dialog`、`@radix-ui/react-dropdown-menu`
- `@stripe/stripe-js`、`tailwindcss-animate`

フォームは `useActionState` を使い、決済はサーバーからStripe Checkoutへ送っている。これらを削除する効果は依存管理・インストール・更新対象の削減。ブラウザ配信量の削減効果は未計測で、未importの依存がそのまま配信されるとは限らない。`react-dom` はNext.jsの実行に、`@supabase/supabase-js` は `@supabase/ssr` のpeer dependencyとして必要なので、この判定に含めない。

`src/lib/works/actions.ts` の旧 `validateAssetAction`（93行）もimport経路がなく、現行UIは `step-actions.ts` を使っていた。再検証処理が二つ残り、所有者確認の内容が食い違っていたため、現行の認可を直したうえで旧Actionを削除した。

### 2. 同一リクエスト内の認証とデータ取得の重複（小〜中）

[印刷キューページ](<../src/app/(admin)/admin/print-queue/page.tsx>) は一覧・集計・フィルターの3取得関数を呼び、それぞれが [requireAdmin](../src/lib/auth/guards.ts) で `auth.getUser()` と役割の取得を行う。[管理レイアウト](<../src/app/(admin)/layout.tsx>) も同じ確認を行い、表示名はさらに別取得。レイアウトとページを描画するコード経路だけで4回、Proxyも含めると5回の `getUser()` 呼び出しがある。これは静的な呼び出し数で、ネットワーク実測値ではない。

[checkout/queries.ts](../src/lib/checkout/queries.ts) も本人確認後に `getCart()` で再確認し、カートが読んだ価格ビューを内訳取得のためにもう一度読む。

同一リクエストの検証済みユーザー・プロフィールを再利用し、カート取得結果に価格内訳も含める。ActionやRPCの認可は維持し、ユーザーを跨ぐキャッシュは作らない。単にガードをレイアウトだけに集めると更新の入口が無防備になる。

### 3. アプリ側でDBの検索・集計を組み立て直している（中）

| 対象 | 現状と影響 | 簡素化 |
| --- | --- | --- |
| [作品検索 `listWorks`](../src/lib/works/queries.ts) | タグ2種・サイズごとにIDを先に取得し、配列の積集合を作ってDBへ戻す。画像・価格の追加取得まで含め最大6問い合わせ。前段のID取得はページングされていない | タグ・サイズの条件をDBの結合・存在条件へまとめ、絞り込み後にページングする。取得関数はその結果を画面用に整える |
| [運営売上 `getSales`](../src/lib/ops/queries.ts) | 精算・明細・払込を取得し、JavaScriptで合計・月別・クリエイター別に集計 | 集計をDBで行い、明細一覧は別にページングする |
| [クリエイター売上 `getCreatorDashboard`](../src/lib/sales/queries.ts) | 全期間の明細を取得してから月別に絞り、8か月分を繰り返し集計 | 対象期間の集計値と直近明細だけを取得する |

[ローカル設定](../supabase/config.toml) のAPI行数上限は1,000件。上記のページングのない取得がこの上限に達すると、検索対象や集計対象が欠ける構造になっている。小さいシードでは現れない正確性の問題でもある。改善は対象クエリ・ビューに絞り、汎用検索フレームワークは不要。

### 4. 金額の按分・料金計算が二重化している（中・優先度高）

[運営売上](../src/lib/ops/queries.ts) は按分した金額の端数を最後の明細へ寄せる。一方、[creator_item_settlements](../supabase/migrations/0019_creator_sales_payouts.sql) は明細ごとに四捨五入し、`creator_payout_balances` はその値を合計する。

例えば受取額101円を同額の2明細へ配ると、運営側の式は **51円＋50円**、SQLの式は **51円＋51円** になる。両方の式をローカルで確認した。残高ビューも明細の値を積み上げるため、単なる表示方法の差ではない。端数の帰属順を決めた一つのDB計算を両画面・残高で使い、合計保存と複数クリエイターのケースを検証する。

ほかにも [個別見積りフォーム](../src/components/custom-orders/quote-form.tsx) の概算は基本作業料 `handling_base_yen` を含まず、[解析の既定値](../src/lib/print/estimate.ts) と作品登録画面の手数料率フォールバックは10%のまま。現行ローカル料金表は基本料0円・手数料20%なので、すべてが現在の注文で顕在化しているわけではない。料金表を使う経路と異常時の扱いを揃える。

注文時の金額スナップショットと現在の料金表は用途が異なるため維持する。過去注文まで再計算する変更にはしない。

### 5. 一つの保存を多数の更新で実現し、トリガーの内部事情までアプリが知っている（中）

[saveWorkInfoAction](../src/lib/works/step-actions.ts) は作品・タグ・内寸・サイズ別価格を順番に更新する。原寸変更時は他サイズの内寸をNULLへ戻し、変更していない `scale_ratio` を1件ずつ書き直してトリガーを再起動している。手順が長く、途中失敗すると一部だけ保存される。

作品情報の保存を一つのトランザクションへまとめ、原寸からの再計算もその中で完結させる。[解析結果の保存](../src/lib/works/asset-validation.ts) も計算終了後のDB反映を一度に確定させる。[運営操作](../src/lib/ops/actions.ts) の「印刷完了＋在庫台帳」「検品＋チェック結果」も同じ対象。認可・許可する状態遷移・競合時の確認はその操作内で行う。

### 6. 小さな共通処理が別機能のモジュールに置かれている（小・後回し）

金額表示 `yen` が作品カード・運営ラベル・フォームに分散し、別画面が作品カードから関数だけをimportしている。メール送信は `siteUrl` を決済用の [stripe.ts](../src/lib/payments/stripe.ts) から読む。表示用の金額関数とサイトURLの設定を、それぞれ用途の合う小さなモジュールへ移せば十分。

似た月選択UIやフォームのクラス名もあるが、差が小さいうちは優先度を下げる。`ops/actions.ts` は640行、`ops/queries.ts` は746行あるものの、まず重複計算と多段階更新を減らし、その後に読みづらさが残る業務だけを分割する。

## 採用範囲・実測を決めてから簡素化するもの

### 7. 保留機能と旧データモデルが現行スキーマに残っている

生成されたDB型を除くアプリコードでは、次の7テーブルへの参照を確認できなかった。現行publicビューからの参照もなかった。

| 対象 | 判断に必要なこと |
| --- | --- |
| `nui_scans`、`nui_assets`、`tryon_renders` | READMEで保留とされるアストラ連携。キャッシュ無効化トリガーなど関連処理も存在するため、使う時期がなければ一式を廃止候補にする |
| `coordinate_posts`、`coordinate_post_pins` | コーディネート投稿を今後提供するか。現行UIは未実装 |
| `user_nui_sizes` | 現行のマイぬいUIは `nui_profiles` を使用。旧モデルからの移行状況を確認する |
| `work_assembly` | 組立情報を独立機能として実装するか。既存のパーツ印刷指示との役割を確認する |

未参照だから直ちに削除可能とは限らない。外部環境のデータ・利用者・SQL内の依存を確認し、廃止する場合は新しいマイグレーションで行う。過去のマイグレーションは消さない。空テーブルの数から実行速度の悪化を断定せず、仕様・権限・生成型を読む負担として評価する。

### 8. 旧課金方式と、UIより広いアセットモデル

[0006](../supabase/migrations/0006_print_ops.sql) の `fee_billing` は `bundled` / `separate` の二方式を持ち、作品登録UIも分岐する。一方、カートからの購入画面・個別見積りは印刷代行費を加算する前提で作られている。ローカルの有効料金表は `separate`。現行仕様がこれに固定なら旧方式を終了し、二方式を維持するなら購入まで一貫した計算が必要。

`work_assets` は複数・サイズ別のデータを表せるが、現行 [registerAssetAction](../src/lib/works/step-actions.ts) は作品の全アセットを削除して1件を作る。1作品1データを正式な制約にするか、サイズ別データを扱うかを揃える。現状の「先に旧データを削除する」差し替えは、新データの登録・解析失敗でも旧データを失うため、仕様選択に関わらず改める。

### 9. ZIP/XMLの自作処理と、HTTP内での同期解析

[zip.ts](../src/lib/print/zip.ts) は94行、[threemf.ts](../src/lib/print/threemf.ts) は297行。ZIPは依存削減、XMLは大きなメッシュへの性能を理由に自作されている。ZIPの展開にはアプリ独自の展開後サイズ上限がなく、XMLの属性読み取りは二重引用符専用で、モデルファイルのパスも固定されている。

この範囲は独自の3D判定ロジックと切り分け、代表ファイル・境界入力・処理時間・メモリを確認したうえで、保守されている汎用実装への置換を比較する。現時点で置換先や速度改善は確定していない。

[asset-validation.ts](../src/lib/works/asset-validation.ts) はServer Actionから同期の解析関数を実行する。大きな入力や同時実行時の処理時間は未計測。最初に入力・展開後サイズ・計算量の上限と実測を整え、必要性が確認できた場合だけ処理の分離を検討する。

### 10. 定期実行の運用先が二つになる設計

見積りの期限切れは [0023](../supabase/migrations/0023_quote_expiry_cron_email.sql) のpg_cronで実装され、READMEはメール配信にEventBridgeを案内している。本番メールcronの配線はREADME上も未完了で、今回AWS環境は調べていない。配備時に監視・再試行・設定場所を増やす必要があるかを確認し、可能なら定期実行の運用先を揃える。通常の通知生成をDBトリガーに置く方針は維持する。

## 簡素化と併せて優先する不具合

以下は上記の削減案とは別に優先すべき事項。再解析・決済・保存・メールの指摘はコード経路の確認に基づき、攻撃リクエスト、実決済、送信失敗、並行更新の再現は今回行っていない。

| 優先度 | 根拠と影響 | 最小の対応 |
| --- | --- | --- |
| 高 | [revalidateAssetAction](../src/lib/works/step-actions.ts) は `workId` の所有者を確認するが、別入力の `assetId` がその作品に属するかを確認せず、service roleによる解析・保存へ渡す | 対象アセットと作品・利用者を結び付けて認可する。自作品のIDと他人のアセットIDを混ぜた入力を拒否する回帰テスト |
| 高 | [Webhook](../src/app/api/stripe/webhook/route.ts) はRPCエラーでも成功応答。[注文完了ページ](<../src/app/(shop)/checkout/complete/page.tsx>) にも更新処理があり、本人の注文確認より先に実行する | 支払い反映を共通関数へまとめ、入口ごとに認証とエラー応答を適用。ページ描画から更新を外す |
| 高 | [placeOrderAction](../src/lib/checkout/actions.ts) はStripeキーがなければ環境を問わず支払い済みにする。注文作成後のCheckout Session作成失敗に再開経路がない | 開発決済は開発環境と明示設定に限定。設定不足を注文作成前に検出し、同じ注文で決済を再開できるようにする |
| 高 | [mail/dispatch.ts](../src/lib/mail/dispatch.ts) は送信前に `emailed_at` を更新するため、その直後のプロセス停止で未送信の通知が処理済みになる。また最初の200件を取得後にdailyの時刻を判定するので、未到来のdailyが200件並ぶと後続のinstantが選ばれない | 送信対象時刻を取得条件に含める。処理中の確保と送信成功を区別し、期限付きの確保・再試行を設ける。既存DBで扱える範囲から始める |
| 中 | [運営](../src/lib/ops/queries.ts)・[カート](../src/lib/cart/queries.ts)・売上などがDBエラーを空配列や0へ変換する | 取得失敗と本当の0件を区別する。売上・価格・在庫は不明な値を成功表示しない |

金額の按分不一致と多段階保存の途中確定も優先度は高い。詳細は項目4・5を参照。

## 開発・検証の負担

- READMEのセットアップは `.env.local.example` をコピーするが、そのファイルが存在しない。新しい環境で手作業が必要になる。秘密値を含まない設定例と、実行できる開始手順を揃える。
- [analyze-file.ts](../scripts/analyze-file.ts) に記載された `node --experimental-strip-types scripts/analyze-file.ts` は、Node 24.13.0で `ERR_MODULE_NOT_FOUND` になった。引数処理へ進む前に拡張子なしのimport解決で失敗する。解析器を変更する前に検証経路を復旧する。
- 既存SQLスクリプトには結果の表示だけで期待値を自動判定しないものがある。前回追加した認可・通知の44件以外にも、按分・解析入力・保存のロールバック・再試行を変更時の検証対象にする。表示だけの小さな部品まで一律にテスト基盤を増やす必要はない。
- READMEと複数の引き継ぎ資料に旧仕様・現在の実装・将来案が混在する。現行の起動手順はREADME、診断は本書、過去の経緯は引き継ぎ資料へ寄せる。[HANDOFF](../HANDOFF.md) の料金の丸め・通知生成・内寸の導出など、現在も必要な設計判断は維持する。

## 維持する構成と次の実装順

機能別の小さな関数、Server ComponentsとServer Actions、利用者権限のDBクライアントとRLS、DB側の制約・金額スナップショット・通知・注文状態導出、3D解析の純粋な計算部分、生成されたDB型を基盤として使う。

単純な取得・更新は既存のqueries/actionsで完結させる。複数の入口に重複した処理は共通関数へ、複数テーブルで成立する更新は一つのRPCへまとめる。このプロジェクトで現時点からRepository、DIコンテナ、汎用ワークフロー、機能ごとのサービス層を追加する根拠は見つからなかった。

1. **認可と決済の穴を閉じる。** アセット所属の確認、開発決済の条件、支払い反映・再試行をそれぞれ小さな変更として検証する。既存のDB認可修正は維持する。
2. **低リスクの不要物を除く。** 未使用の依存6件と旧Actionを除去し、設定例・解析スクリプトを整える。型チェック・lint・ビルド・解析起動を確認する。
3. **問い合わせと計算の重複を減らす。** 同一リクエストの認証再利用、カート価格の再取得廃止、検索・売上のDB集計、按分計算の統一。問い合わせ回数、1,000件を超える対象、端数を確認する。
4. **保存と配信の失敗境界を揃える。** 作品情報・解析結果・運営操作を業務単位で確定し、メールは処理中と送信済みを分ける。途中失敗・同時操作・再実行で検証する。
5. **仕様を絞って残りを削減する。** 旧課金方式、未実装テーブル、アセットの多重性を判断し、ZIP/XMLの置換は実測後に決める。実装済みの機能廃止をこの診断だけで確定しない。

完了の尺度は、同じ操作に必要な問い合わせ・計算式・分岐・変更箇所が減り、失敗時も状態が整うこと。ファイル分割数や導入した設計パターンの数では評価しない。
