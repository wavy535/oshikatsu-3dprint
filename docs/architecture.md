# 全体の問題点と改善状況

2026-09-09。`refactoring`ブランチでの診断と実装状況。現在の対象はAWSで動くデモ環境で、実課金は不要。アプリ内通知とメール配信は残す。

## 現在の構成

Next.jsのServer Components / Server Actionsと機能別の `src/lib/*` を基本にする。単純な取得・変更はqueries/actionsに置き、複数テーブルを一度に確定する業務はDBのRPCへまとめる。Repository、DIコンテナ、機能ごとのサービス層は一律に追加しない。

AWSでは通常のNode.jsコンテナとして動かし、Auth・PostgreSQL・Storageは当面Supabaseを継続する。RDS・Cognito・S3への移行は、SupabaseのAuth/RLS/Storage APIとの結び付きを置き換える別の作業になる。[配備構成と設定例](../infra/aws/README.md)を参照。

## 対応済み

| 対象 | 変更と確認 |
| --- | --- |
| RPC・通知の認可 | 0027・0028で匿名操作と通知内部関数を制限。0032で通知の利用者更新を `read_at` に限定 |
| アセットの再解析 | 作品とアセットの所属を利用者権限で照合し、解析側も認可済みの作品に限定。使われない旧Actionを削除 |
| 不要な依存 | 未使用の直接依存6件とStripeサーバーSDKを削除。AWSメール送信には公式のSES SDKを使用 |
| 認証・データ取得の重複 | リクエスト内で認証とプロフィールを共用。カートの価格内訳を購入画面でも使い、再取得を削減。価格・送料の取得失敗を0円表示しない |
| 精算・概算 | 0030のSQLを運営・クリエイター・残高で共用。累積比率の差で端数を配り、合計を保存。個別見積りも共通の印刷費計算を使用 |
| デモ注文 | 0031の `place_demo_order` で作成・確定・在庫・カート・印刷ジョブを一度に更新。再送は同じ注文を返す。途中失敗のロールバックを検証 |
| 実決済の連携 | SDK・Webhook・Session照会・再開分岐・設定を削除。旧DB関数はAPI実行を停止し、既存データとマイグレーション履歴は保持 |
| メール配信 | SES / Mailpitを明示選択。0032で送信済みと期限付き確保を分離し、停止後に再取得。対象時刻をLIMITの前に絞り、未到来のdailyによるinstantの遅延を防止 |
| AWSの実行形態 | Next.js standalone、非rootのDockerコンテナ、依存サービスを呼ばないヘルスチェック。秘密値はビルドへ含めず実行時に渡す |
| 開発・検証 | Node.js 24、環境変数例、Vitest・pgTAP、Node.jsで動く3D解析スクリプトと四面体のfixture |

デモ注文には `is_demo=true` と安定したcheckout request IDを記録する。アプリでは実際の請求がないことを表示する。`NODE_ENV=production` のAWS環境でもデモを確認できる。外部決済の履歴がある既存注文はデモへ変換しない。

通知メールは通常の同時実行による重複を避けるが、SES受理直後にDBへの記録が失敗した場合などは再送され得る。7日を超える通知を送信対象から外す既存仕様も維持している。完全な一回配信や無期限の再試行は保証しない。

## 次に改善する対象

### 検索・売上の取得上限とDB集計

| 対象 | 問題 | 次の変更 |
| --- | --- | --- |
| [作品検索 `listWorks`](../src/lib/works/queries.ts) | タグ・サイズ別のIDを先に全取得してJSで積集合にし、DBへ戻す。最大6問い合わせ。前段はページングなし | 条件をDBの結合・存在条件へまとめ、絞り込み後にページング |
| [運営売上 `getSales`](../src/lib/ops/queries.ts) | 共通化した精算値は使うが、明細・払込を全取得してJSで集計 | DBで集計し、明細一覧はページング |
| [クリエイター売上](../src/lib/sales/queries.ts) | 全期間を取得した後に月別集計を繰り返す | 対象期間の集計値と直近明細だけを取得 |

[API行数上限](../supabase/config.toml)は1,000件。これを超えると上記の対象が欠ける。単に上限値を増やすのではなく、DBで絞り込み・集計する。価格以外にもDBエラーを空配列・0に置き換える取得処理が残っており、特に売上では「取得失敗」と「実績なし」を区別する。

### 作品・解析・運営操作の多段更新

[saveWorkInfoAction](../src/lib/works/step-actions.ts)は作品・タグ・内寸・サイズ別価格を順番に更新する。原寸変更時に他サイズの内寸をNULLへ戻し、同じscale_ratioを書き直してトリガーを動かすなど、アプリがDB内部の更新手順を知りすぎている。一つの保存RPC内で再計算まで確定させる。

[解析結果の保存](../src/lib/works/asset-validation.ts)、[印刷完了＋在庫台帳・検品＋チェック結果](../src/lib/ops/actions.ts)も同じ課題がある。許可する状態遷移・認可・ロックを操作内で揃え、途中失敗・同時操作で検証する。

[registerAssetAction](../src/lib/works/step-actions.ts)は新データの登録前に既存アセットを削除するため、失敗すると旧データを失う。新データを検証してから差し替える。DBは複数・サイズ別アセットを表せる一方、現在のUIは1作品1データなので、その対応範囲も揃える。

### 3MFの汎用処理と解析の上限

[ZIP処理](../src/lib/print/zip.ts)と[3MF XML処理](../src/lib/print/threemf.ts)を自作している。展開後サイズの明示的な上限がなく、属性は二重引用符専用、モデルファイルのパスも固定。代表ファイル・境界入力・処理時間・メモリを確認して、保守されている汎用実装との置換を比較する。

3Dの幾何計算自体はアプリ固有の処理として維持する。HTTPリクエスト内の同期解析について、入力・展開サイズ・計算量の上限と計測を先に整える。必要性が分かる前から別ワーカーやジョブ基盤を増やさない。

## 仕様を確認してから削減するもの

| 対象 | 状況・判断に必要なこと |
| --- | --- |
| `nui_scans` / `nui_assets` / `tryon_renders` | 保留のアストラ連携。キャッシュ無効化等のDB依存がある |
| `coordinate_posts` / `coordinate_post_pins` | コーディネート投稿。現在のUIに未実装 |
| `user_nui_sizes` | 現行のマイぬいUIは `nui_profiles` を使う。旧データの移行状況を確認 |
| `work_assembly` | 現行のパーツ印刷指示との役割、独立した組立機能を提供するか |
| `fee_billing=bundled` | 有効料金表は `separate`。購入画面・注文は印刷代行費を加算する前提で、二方式の整合が取れていない |

上の7テーブルは生成型を除くアプリから未参照。外部環境のデータ・SQL依存は未確認なので、過去のマイグレーションを消したり、単に未参照という理由でテーブルを削除したりしない。空テーブルの数から実行性能を断定せず、仕様・権限・生成型の保守負担として評価する。

金額表示 `yen` がカード・運営ラベル・フォームに分散し、別画面がカードから表示関数だけをimportしている点も後で整理できる。サイトURLは既に決済から切り離し、実行時設定の `SITE_URL` にした。表示上の小さな重複は、取得上限と保存の不整合より優先度を下げる。

## 検証と範囲

- アプリのテスト21件、DBのpgTAP 97件。注文の認可・再送・途中失敗、精算の端数、通知の権限・確保期限・送信対象時刻、メール成功／失敗を検査
- 型チェック・lint・本番コンテナビルドが成功。コンテナ上でログイン・通知一覧・注文フォームPOST・注文完了・再送時の同一注文IDを確認。注文は実課金なしで印刷待ちまで進む
- 実行ユーザーUID 1000、イメージ内に環境変数ファイルなし。秘密値を渡さない起動でもhealthは200、未設定cronは503。設定済みcronへの未認証POSTは401。cron設定SQLはローカルのトランザクション内で登録を確認してロールバック
- マイグレーション0027〜0032の適用先はローカルSupabaseのみ。AWSリソース作成、SESの外部送信、実決済は行っていない
- 全RPC・RLSの網羅監査、外部環境の利用状況、ブラウザ操作、負荷・メモリ・バンドルサイズの測定は未実施
