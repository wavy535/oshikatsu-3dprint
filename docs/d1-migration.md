# D1の設計と旧DBとの差異

## 採用した構成

- 配備先は yumaboda.official@gmail.com のCloudflareアカウント。既存データの移行はしない。
- PostgreSQL / Hyperdrive / Neonへの実行時依存をなくす。WebはWorkers、DBはD1、ファイルはR2、造形検証・AR変換は既存の非公開Containersを使う。
- メール送信は当面行わず、メール未確認でも一般会員登録を許可する。確認済みフラグは偽装しない。
- クリエイター申請は停止する。再開時の条件は「確認済みメール＋規約同意＋運営承認」。SMSは使わない。
- 実決済・出金は未実装。AI編集は [AIチャット](design-ai-chat.md) を参照。

## 互換性の基準

`3248d66` のローカルPostgreSQLを比較対象とする。`scripts/d1/capture-oracle.mjs` はテーブル定義、制約、索引、行・列の権限、関数と料金計算・注文の結果を取得する。ユーザー行・接続情報は出力しない。`db/oracle/postgres.json` は移行用の固定資料であり、本番Workerには含めない。

D1にはRLSや対話的トランザクションがない。読み取りはユーザー別の可視性を持つSQLビュー、更新はSQLトリガーで検証する。認証済みセッションから得たユーザーIDの設定、対象クエリ、IDの消去を同一のD1 `batch` に含める。途中で失敗すると全体が戻るため、他リクエストへIDが残らない。内部トリガーの更新だけは同じトランザクション内で権限を昇格する。

読み取りもD1の主系でbatch処理する。読み取りレプリカやキャッシュは使っていない。分散読み取りを導入する場合は、利用者IDを明示して読み取りを制限する方式へ変更し、既存の権限テストを通す。DBへの直接アクセスや任意SQLを受け付けるAPIは提供しない。

複数テーブルを更新する処理はD1 `batch` にまとめる。行ロックやコールバック式トランザクションは使わない。注文の在庫引当・一意な要求ID・数量条件は同じバッチ内で検証する。

## 移植時に確認する差異

- SQLiteの真偽値は0/1、配列とJSONはJSONテキスト。DB境界で型を復元する。
- 業務の日時はUTCのISO文字列で保存する。日本時間での集計は明示的に変換する。
- 円単位の金額と丸めは旧DBの計算結果で比較する。SQLiteの整数除算を避け、按分時も総額を保持する。
- SQLiteにはENUMがないためCHECK制約で許容値を限定する。
- 権限制御、同時注文、ロール変更、印刷用ファイルのスナップショット、部分失敗時の巻き戻しを配備前に確認する。

## 具体的な差異と検証

- 旧DBの72通りの料金・材料計算と、注文・明細・印刷ジョブのスナップショットに一致する。注文要求IDの再実行、別会員による最後の在庫の同時購入、下流処理失敗時の注文・在庫・カートのrollbackを確認した。
- 精算の総額と端数配分、他クリエイターの明細非表示、ぬい寸法の推定・実測優先・0.1mm丸めを旧SQLの期待値で確認した。
- 通知のread_atだけを書ける列権限をD1トリガーに移植。配信リース・通知の作成・他会員の既読操作を保護する。メール配信は停止中。
- SQLiteのAFTERトリガーによる変更は同じINSERTのRETURNINGに現れない。IDを受け取り、計算済み列は保存後に読み直す。
- 認証テーブルの権限なし読み取りは、旧DBのpermission errorに対してD1では空配列を返す。データは開示しない。非公開テーブルへのSQLやスキーマ操作は、アプリのクエリ実行処理で拒否する。
- 作品の保存は更新番号をバッチ内で確認し、競合したら最新の状態を読み直し、最大3回までやり直す。モデル解析中に編集された状態を上書きしない。
- SQLiteの整数・REALを使い、業務日時はUTCのISO文字列に統一する。PostgreSQLの型名・SQLSTATE全体の互換は提供しない。円額・小数丸めは個別に比較する。
- マイグレーションのCASE式は括弧で囲む。WranglerのSQL分割がCASEのENDをトリガー終端と誤認する問題を避け、式の結果・拒否条件を維持する。`tests/d1-migration-sql.test.ts` で検査する。
- Better Authの一般SQLite introspectorはD1予約テーブルに触れてSQLITE_AUTHとなる。登録済みアプリテーブルだけを実際に検査するD1用introspectorでスキーマ検査を維持した。

派生ビューは `db/d1/0003_views.sql` を手動で管理する。他の初期マイグレーションは固定catalogから `npm run db:generate` で生成できる。配備後は適用済みSQLを書き換えず、新しい番号のマイグレーションを追加する。ローカルfixtureは `scripts/d1/seed-local.mjs` からのみ作成し、本番へ転送しない。

## 検証

旧PostgreSQLのSQLテストは比較資料として保持する。D1では固定した料金・注文の期待値と権限・競合・巻き戻しを検証し、実workerdでマイグレーション・要求間のID分離も確認する。旧SQLテストをD1で直接実行することはできない。

実行条件と検証範囲は [テスト方針](testing.md)、リモート適用は [配備手順](../infra/cloudflare/README.md) を参照。
